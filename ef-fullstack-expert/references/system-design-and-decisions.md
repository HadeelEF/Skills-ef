# تصميم الأنظمة وقرارات المعمارية بمستوى Principal

اقرأ عند تصميم نظام من الصفر، أو قرار يصعب عكسه، أو مفاضلة بين تقنيات،
أو وضع معايير فريق. السؤال ليس «كيف أكتب الكود؟» بل «ما التصميم المناسب
للنظام كاملًا، وما أثره على الأداء والأمان والفرق والتشغيل والكلفة لسنوات؟».

## منهج التصميم

1. **المتطلبات الحاكمة**: المستخدمون والجهات، الرحلات الحرجة، تصنيف البيانات،
   الحمل المتوقع الآن وبعد 3 سنوات (تقدير موسوم)، التوافر وRPO/RTO، التكاملات،
   قيود الاستضافة والترخيص، حجم الفريق ومهاراته.
2. **الحدود**: bounded contexts/modules وملكية البيانات وحدود الثقة. ابدأ
   Modular Monolith ما لم يوجد سبب موثق للتوزيع.
3. **المسارات الحرجة**: لكل رحلة حرجة اكتب الطلب → التفويض → المعاملة → الآثار
   اللاحقة → الاستجابة، مع نقطة الفشل والضمان.
4. **السعة**: RPS، اتصالات DB، حجم البيانات، نقطة التشبع الأولى المتوقعة.
5. **الفشل**: مصفوفة لكل اعتماد (قالب failure-mode-matrix).
6. **التشغيل**: النشر والترحيل والرصد والإنذار والتعافي والمالكون.
7. **الكلفة**: البنية والترخيص والتشغيل والمهارات، ومقارنة بالبديل الأبسط.
8. **ADR** لكل قرار يصعب عكسه، مع الشرط الذي يغيّره لاحقًا.

## مصفوفة القرارات المتكررة

| القرار | اختر الأول عندما | اختر الثاني عندما | الكلفة الخفية |
| --- | --- | --- | --- |
| Modular Monolith / Microservices | فريق واحد أو قليل، معاملات متداخلة، نشر موحد مقبول | فرق مستقلة بإيقاع نشر مختلف، توسع أو عزل أمني مختلف جذريًا | الخدمات: شبكة، اتساق نهائي، تتبع موزع، نسخ عقود، تشغيل N مرة |
| REST / gRPC | متصفح، عملاء خارجيون، بوابة API، تشخيص بشري | داخلي عالي الحجم، عقود typed، streaming | gRPC: HTTP/2 عبر كل proxy، أدوات تشخيص، gRPC-Web |
| SQL / NoSQL | علاقات وقيود ومعاملات وتقارير | نموذج وثائقي أو key-value بحجم/توزيع لا يلائم العلائقي | NoSQL: قيود التكامل تنتقل إلى الكود، مهارات جديدة |
| EF Core / Dapper | CRUD ومعاملات وتتبع ونموذج يملكه التطبيق | قراءات معقدة مقاسة، stored procedures قائمة، bulk | خلطهما: ملكية الاتصال والمعاملة |
| متزامن / غير متزامن | المستخدم يحتاج النتيجة فورًا والعملية قصيرة | عمل طويل، اعتماد غير موثوق، تسوية حمل | غير المتزامن: حالة، تكرار، رصد backlog، UX للانتظار |
| Redis / قاعدة البيانات | قراءة ساخنة مقاسة، multi-instance، stale مقبول | الصحة تحتاج اتساقًا، الحمل لا يبرر | Redis: إبطال، فشل، أمن، مكوّن تشغيلي إضافي |
| Hangfire / broker | مهام تطبيق داخلية مخزنة في DB، فريق واحد | تكامل بين أنظمة، حجم عالٍ، fan-out | broker: تشغيل، DLQ، ترتيب، مهارات |
| IIS / Containers | بنية Windows قائمة، فريق يجيدها، تطبيقات قليلة | منصة orchestration قائمة، كثافة نشر، بيئات متطابقة | containers بلا منصة = تشغيل إضافي دون عائد |

لا تقبل من نفسك «لأنها best practice». اذكر الفائدة والكلفة والمخاطر والبديل.

## سيناريو مرجعي: نظام مؤسسي 10,000 مستخدم متزامن

React + ASP.NET Core + SQL Server + Redis + Jobs + SignalR + ملفات + Email/SMS +
تكاملات خارجية + صلاحيات معقدة + audit.

- **النشر**: Modular Monolith API (stateless) بنسختين إلى أربع خلف LB، و Worker
  Service مستقل كـWindows Service للمهام، وReact كملفات ثابتة أو BFF عند حساسية tokens.
- **السعة (افتراض)**: طلب/30ث للمستخدم ≈ 333 RPS، ذروة ≈ 1,000 RPS. بزمن DB
  20ms ≈ 20 اتصالًا نشطًا متوسطًا؛ اضبط pool لكل نسخة واختبر الذروة.
- **البيانات**: SQL Server واحد للكتابة مع HA وفق edition، فهارس من query shapes،
  RCSI بعد تقييم tempdb، وread replica أو read model للتقارير الثقيلة.
- **التفويض**: OIDC مع IdP المؤسسة، policies + resource authorization في كل use
  case، نطاق الجهة/الإدارة في الاستعلامات والتصدير والـjobs، audit في نفس المعاملة.
- **Cache**: Redis لبيانات مرجعية وقراءات ساخنة مقاسة، مفاتيح بالنطاق، تجاوز عند
  الفشل، وData Protection keys في مخزن مشترك محمي (ليس cache قابلًا للإخلاء).
- **Jobs/Integrations**: outbox في SQL للإشعارات والتكاملات، worker مع lease
  وidempotency، Email/SMS عبر مزود بمفتاح idempotency أو سجل تسليم.
- **Realtime**: SignalR للإشعارات فقط مع backplane، والحقيقة تُجلب من API.
- **الملفات**: object/shared storage خاص، metadata في SQL بحالة، فحص قبل الإتاحة.
- **الرصد**: OpenTelemetry traces من الواجهة إلى الـworker، SLOs للرحلات الحرجة،
  إنذارات على عمر outbox وأخطاء 5xx وp95.
- **النشر**: expand/contract، blue/green أو rolling مع readiness وdrain، migration
  منفصلة، rollback متوافق مع البيانات.
- **ما الذي يغير القرار**: فرق مستقلة متعددة، أو حمل كتابة يتجاوز خادمًا واحدًا
  بعد تحسينه، أو متطلب عزل تعاقدي لكل جهة.

## معايير الفريق

ضع لكل مشروع وثيقة قصيرة قابلة للفرض آليًا قدر الإمكان:
- **الكود**: analyzers وnullable وwarnings as errors للجديد، تنظيم features، لا
  Shared مستودع لكل شيء، حدود modules باختبار معماري عند الخطر.
- **API**: تسمية الموارد، ProblemDetails بمفاتيح خطأ ثابتة، pagination/sorting
  موحد، ETag للتعديل، Idempotency-Key للعمليات الحساسة، OpenAPI diff في CI.
- **السجلات**: message templates، حقول إلزامية (traceId، tenant/scope، operation)،
  قائمة ممنوعات (tokens، كلمات مرور، PII كاملة)، مستويات بدلالة محددة.
- **الاختبارات**: ما يُختبر على SQL Server حقيقي، اختبارات التفويض لكل endpoint
  حساس، اختبارات التزامن للـinvariants.
- **قاعدة البيانات**: تسمية، أنواع قياسية (datetime2، decimal بدقة)، FK وقيود
  إلزامية، مراجعة SQL الناتج من migrations، لا SELECT * في كود الإنتاج.
- **النشر**: artifact واحد يُرقّى بين البيئات، config خارجي، checklist ما بعد النشر.

المعيار الذي لا يُفحص آليًا أو في المراجعة يتآكل؛ اختر القليل الذي يمكن فرضه.

## الكلفة والفريق

- قارن الكلفة الكلية: خوادم، تراخيص (SQL Server edition، مكتبات تجارية، خدمات
  مدارة)، تشغيل ومراقبة ومناوبة، وتدريب. مكوّن جديد = مالك تشغيلي جديد.
- اختر ما يستطيع الفريق تشغيله ليلًا عند العطل، لا ما يبدو أحدث.
- خطط للتطور: ما الحد الذي يجعل التصميم الحالي غير كافٍ، وما خطوة الانتقال
  التالية، دون بنائها الآن.
