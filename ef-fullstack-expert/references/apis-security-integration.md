# APIs والأمان والتكامل

## نفذ API قابلة للاستهلاك

اختر Minimal APIs أو Controllers حسب المشروع، واجعل routes ومصادر
binding صريحة عند احتمال الالتباس. افصل DTOs المدخلة عن entities،
وحدد الحقول القابلة للكتابة. ميز PUT/PATCH وPOST وGET وفق معنى العملية؛
لا تسمح لـGET بإحداث تغيير. استعمل نتائج typed عندما تحسن عقد OpenAPI.

راجع model validation الفعلي في [ApiController] وMinimal APIs وإصدار
ASP.NET Core؛ لا تفترض تطابق السلوك التلقائي. أعد validation errors
بأسماء حقول يستطيع العميل ربطها، وProblemDetails وفق العقد. ميز
201/Location عند إنشاء مورد، و204 بلا body، و202 للعمل غير المكتمل.

اضبط route/query/form/body وContent-Type على الطرفين. قد ترجع صفحة
Razor HTML، بينما يتوقع عميل API JSON؛ لا تعيد صفحة login كاستجابة نجاح
لطلب بيانات. تحقق من سلوك cookie authentication وredirect و401/403
في الإصدار ونوع endpoint، واختبر انتهاء الجلسة فعليًا.

حدّد pagination والترتيب والفرز والبحث المسموح، وأحجام body/files،
وسياسة rate limiting والـtimeouts حيث تلزم. اجعل cache/output caching
متوافقًا مع هوية المستخدم والنطاق؛ لا تشارك استجابة خاصة بين مستخدمين.
راجع رفع الملفات وantiforgery حسب binding ونوع المصادقة والإصدار.

أنشئ أو حدّث OpenAPI وأمثلة الاستخدام والـclient في نفس التغيير.
اختبر HTTP حقيقيًا عبر host اختبار مناسب عند توفره، بما يشمل middleware
وauthorization وserialization؛ استدعاء دالة endpoint وحدها لا يثبتها.
احتفظ بتوافق العملاء وأعلن التغييرات الكاسرة مع خطة انتقال.

## صمم عقدًا قابلًا للاستخدام والتطور

حدد methods وroutes وDTOs وأكواد الحالات والأخطاء والتحقق والصفحات
والفرز وحدود الطلب. وثق العقد بـOpenAPI المتوافق مع المشروع. راجع
شكل الهوية والتواريخ والمبالغ والقيم الاختيارية وenums بين C# وTypeScript.
استخدم versioning عندما توجد حاجة لدورة توافق واضحة، لا كطبقة شكلية.

حدد سلوك timeout/cancellation وتكرار العمليات. عملية طويلة يمكن أن
تعيد 202 مع مورد لحالتها إذا كان العقد يدعم ذلك؛ 202 لا يثبت اكتمالها.
ميز خطأ المدخل عن المنع والتعارض والفشل الخارجي. طبّق نفس العقود في
المسارات العادية والمهام والتصدير.

## افصل الهوية عن التفويض

- اختر OIDC/OAuth أو cookies أو نمط المشروع المعتمد بحسب العميل
  وحدود الثقة. استخدم المكتبات المعتمدة؛ لا تنفذ بروتوكول هوية مخصصًا.
- عند JWT تحقق من التوقيع والمصدر والجمهور والعمر وفق issuer الحقيقي؛
  لا تعتبر فك ترميز token تحققًا منه. لا تستخدم ID token بدل access
  token لاستدعاء API محمي.
- استمد هوية المستخدم من principal موثوق؛ لا تستخدم userId/role/tenant
  مرسلة من العميل لتحديد من هو أو ما يحق له. حافظ على معرف ثابت ملائم
  لمصدر الهوية، ولا تجعل email هوية دائمة تلقائيًا.
- افحص الإذن على **العملية والمورد والنطاق** في الخادم. GUID غير قابل
  للتخمين ليس authorization. اختبر محاولة عضو الوصول لسجل في مساحة
  أخرى، بما يشمل endpoints المباشرة والبحث والمرفقات والتصدير.
- طبق deny-by-default وحدود العضوية والصلاحيات المعتمدة. اختر 403 أو
  404 لسجل خارج النطاق وفق سياسة كشف الوجود في المشروع.
- واجهة المستخدم يمكن أن تخفي إجراءً؛ يبقى enforcement داخل API.

## اختر جلسة متوافقة مع العميل

لـBFF/cookies استخدم HttpOnly وSecure وSameSite المناسب، وحماية CSRF
للعمليات المعدلة. للـSPA المباشر استخدم تدفق OIDC مناسبًا وSDK موثوقًا
واستراتيجية tokens مدروسة؛ لا تضع client secret في متصفح أو تطبيق عام.
عرّف انتهاء الجلسة والخروج و401/403 والتجديد وحدود CORS صراحةً.

تكامل Entra ID أو حسابات الطوارئ متطلب مشروع، وليس افتراضًا عامًا.
عند طلب حساب محلي طارئ، صمم نطاقه وتخزينه الآمن وMFA/سياسة الوصول
المعتمدة وتدقيق استخدامه دون توسيعه تلقائيًا لتسجيل مستخدمين محليين عام.

## راجع الحدود المعرضة للمدخلات

تحقق من البيانات على الخادم، وحدد body/file limits. استخدم parameterized
queries وencoding/sanitization المناسبين للسياق. تعامل بحذر مع HTML
الغني والروابط التي يجلبها الخادم وعمليات import/export والمسارات.
للمرفقات تحقق من النوع والحجم والمحتوى وفق المخاطر، وافصل اسم العرض
عن مسار التخزين، وافحص الإذن عند كل تنزيل. عالج صيَغ الجداول الخطرة
عند تصدير بيانات غير موثوقة إلى CSV/Excel.

راجع URLs الخارجية لمنع SSRF عند وجود جلب مدخل من المستخدم. لا تكتب
مفاتيح أو cookies أو bearer tokens أو بيانات شخصية كاملة في السجلات.
اجعل audit log للعمليات الحساسة قابلًا لربط الفاعل والفعل والوقت والنتيجة،
وبمحتوى وحدود احتفاظ مناسبين.

## اجعل التكامل يتحمل الفشل

وثق endpoint الحقيقي والعقد ومصدر الاعتماديات وطريقة المصادقة.
ميّز sandbox عن الخدمة الفعلية. اضبط timeout وcancellation وretry مع
backoff/jitter حيث يناسب، وراقب أثر retries المتراكبة عبر طبقات متعددة.
استخدم circuit breaker أو bulkhead فقط عندما تلزم سياسة فشل واضحة.

تحقق من توقيع webhooks وإعادة الإرسال وreplay window عند انطباقها.
حدد deduplication والترتيب وdead-letter/recovery للمراسلة. للتكامل مع
Apigee أو Fusion أو غيرهما، اقرأ مواصفات المشروع وواجهات الخدمة الفعلية؛
لا تخترع endpoints أو تفترض وصولًا متاحًا.

مرجع رسمي: [Resource-based authorization](https://learn.microsoft.com/en-us/aspnet/core/security/authorization/resource-based).

لتصميم نموذج الصلاحيات كاملًا اقرأ authorization-architecture، ولسياسات retries
وwebhooks والتكامل الخارجي اقرأ resilience-and-integration-recipes من فهرس المهارة.
