# تصميم الـBackend وتحويله إلى تنفيذ

اقرأ عند تصميم ميزة أو module أو تنفيذ Backend ذي قواعد وتكاملات.
استخدم مع مرجع هيكلة الكود والبيانات والعقود بحسب النطاق. اجعل التصميم
خريطة تنفيذ قابلة للفحص، بحجم المهمة، ولا تؤجل البرمجة إلى وثيقة غير لازمة.

## ابدأ بعقد حالة الاستخدام

حدد actor والنية والنتيجة والبيانات المملوكة والسياق الموثوق. ميز أمر
أعمال مثل Submit/Approve/Cancel عن تحديث entity عام؛ CRUD مناسب عندما
تكون الدلالة CRUD فعلًا. اربط عناصر التصميم بالتنفيذ والدليل:

| قرار التصميم | ما ينفذ في المشروع | دليل ذو معنى |
| --- | --- | --- |
| من يستطيع تنفيذ العملية وعلى أي مورد؟ | policy/resource authorization ونطاق query | مستخدم ممنوع ومورد من نطاق آخر |
| ما الحالات والانتقالات المسموحة؟ | قاعدة في use case/domain وكتابة تحمي السباق | انتقال مسموح وآخر ممنوع وطلبان متداخلان |
| ما المدخلات التي يملكها العميل؟ | command DTO وvalidation وتحويل محدود | رفض حقول/قيم غير مسموحة دون mass assignment |
| ما الثابت الذي يجب ألا ينكسر؟ | constraint أو conditional write/isolation مناسب | فحص invariant على provider ممثل |
| ما الذي يجب أن ينجح أو يتراجع معًا؟ | transaction boundary محدد | فشل بين الكتابات لا يترك حالة جزئية |
| ما الأثر الخارجي وكيف يعاد؟ | adapter وoutbox/job عند الحاجة | تكرار/timeout/restart وفق ضمان العقد |
| ماذا يقرأ العميل بعد العملية؟ | response DTO وversion وread projection | إعادة قراءة تؤكد النتيجة عبر API |

حدد required/optional وnull/absent والوحدات والمبالغ والتاريخ والنسخ،
وعقد الأخطاء وحالة العملية غير المعلومة. لا تستمد actor أو tenant أو
approvedBy أو ownership من body لمجرد وجودها في TypeScript type.

## ضع القواعد في مكان يضمنها

- افصل التحقق من شكل المدخل، والصلاحية، وقاعدة المجال، وضمان التخزين؛
  كل منها يحمي حدًا مختلفًا. لا تجعل FluentValidation async uniqueness
  أو زرًا disabled بديلًا عن قيد قاعدة البيانات أو التفويض الخادمي.
- مثل state transitions عندما يعتمد السلوك على الحالة الحالية. اجعل
  تسجيل الانتقال وفاعل العملية ووقتها ناتجًا خادميًا متسقًا مع commit.
- راجع invariants التي تمتد عبر عدة صفوف: مجموع حصص أو منع حجز متداخل
  لا يحميهما rowversion على كل صف منفرد تلقائيًا. حدد صف التنسيق أو
  constraint/locking/isolation المدعوم، وقِس كلفة التنافس دون قفل عالمي.
- لا تعتبر optimistic concurrency وidempotency وauthorization مفاهيم
  متبادلة؛ الأول لا يمنع تكرار intent، والثاني لا يمنح صلاحية، والثالث
  لا يمنع lost update. اربط كل ضمان بمكان تنفيذه واختباره.
- اختر read model يخدم الاستعلام دون تحميل aggregate كامل؛ صمم projection
  وfilter/sort/pagination والفهارس من query shape وحجم البيانات المتوقع.
  اجعل counts والexports تخضع لنفس نطاق الوصول، وحدد الاتساق المطلوب.

## تتبع مثال الانتقال دون فرض قالب

لعملية Submit نموذجية، حدد أولًا معناها في المشروع. مثال قرار قابل للتكييف:
العميل يرسل المورد والنسخة التي عرضت له؛ الخادم يستخرج هوية الفاعل، ويتحقق
من حقه ومن اكتمال البيانات، ثم ينقل Draft إلى Submitted بشرط النسخة والحالة.
يكتب audit المطلوب في المعاملة نفسها أو يضمن تسليمه حسب عقد التدقيق.

إن كان الانتقال يعتمد على children، يجب ألا يستطيع طلب متزامن تعديلها
بعد فحصها وخارج ضمان المعاملة المختار. قيد UPDATE على parent وحده لا
يكفي إن كانت تغييرات children لا تشارك lock/version discipline نفسه.
حدد نتيجة الطلب المكرر أو القديم، وما إذا كانت هناك حاجة idempotency.
لا تستدعِ البريد ثم تحفظ البيانات؛ سجل عملًا دائمًا بعد نجاح العملية
ضمن آلية موثوقة عند الحاجة، واترك handler قصيرًا وواضح المسؤوليات.

في الواجهة ارسم نتيجة كل عقد: نجاح مع النسخة الجديدة، أخطاء حقول، عدم
سماح، تعارض يحتاج إعادة قراءة، أو timeout يحتاج تحققًا من الحالة. لا
تكرر Submit تلقائيًا لمجرد انقطاع الشبكة، ولا تمسح مسودة المستخدم خفية.
هذا مثال لتتبع الضمانات؛ لا تضف workflow engine أو outbox لميزة لا تحتاجهما.

## نفّذ vertical slice ثم راجعه

1. عدل العقود والسياسات ومخطط البيانات اللازم في موضعها الحقيقي؛ راجع
   البيانات القائمة وbackfill والتوافق قبل migration كسرية.
2. نفّذ endpoint/handler أو PageModel، وتسجيل DI/validators/adapters،
   وصلة persistence الفعلية. حافظ على cancellation وأعمار الموارد؛
   لا تستبدل تكاملًا مطلوبًا بقائمة in-memory أو نجاح ثابت غير معلن.
3. طابق OpenAPI/status/headers/body مع العميل. نفّذ العميل أو مثال
   الاستهلاك المطلوب والأخطاء، ولا تسلم DTOs أو services غير مستخدمة.
4. أضف observability عند الحد المفيد: operation وtrace ومعنى فشل العملية،
   دون تسجيل أسرار أو bodies حساسة. ميز logs عن أثر audit المطلوب.
5. شغّل build والفحوص المناسبة المتاحة. اختبر SQL والقيود والمعاملات
   على provider ممثل؛ mocks وEF InMemory لا يثبتان تلك الضمانات.
6. راجع diff وحالة نجاح وفشل مؤثر ومسار إعادة القراءة. تحقق من عدم
   إضافة abstractions أو packages لا يحتاجها المسار، ثم أكمل نطاق الطلب.

## تسليم عملي

لخص القرارات المؤثرة ومواضع تنفيذها وطريقة التشغيل وما ثبت بالأوامر
والاختبارات. أرفق ترحيلًا/تهيئة لازمة عند وجودها، وسجل قيد البيئة بدقة.
إذا كانت المهمة تصميمًا فقط، قدم حدود المكونات وعقودها وخريطة الملفات
والتتابع ومعايير قبول التنفيذ؛ لا تعرض التصميم بوصفه كودًا مكتملًا.
