# الجداول الكبيرة وواجهات المؤسسات

اقرأ عند بناء قائمة أو جدول بيانات: فلترة وفرز وصفحات وتحديد وإجراءات جماعية وتصدير وتعديل.
أغلب شاشات الأنظمة الداخلية جداول؛ صمم مكونًا مؤسسيًا واحدًا وعقدًا موحدًا مع .NET بدل جدول
جديد لكل شاشة. TanStack Table headless مناسب لنظام تصميم EF. **انتبه للإصدار:** v8 يستخدم
`useReactTable`، وv9 (2026) يستخدم `useTable` مع خيار `features` إلزامي وحالة على TanStack Store،
مع `useLegacyTable` للترحيل. تحقق من الإصدار قبل نسخ أي مثال.

## العقد مع الخادم أولًا

البيانات الكبيرة تُصفّى وتُرتب وتُقسم في الخادم. لا ترسل 100 ألف صف للمتصفح.

```ts
// Request: query string, validated on the server with an allowlist of sortable/filterable fields.
type PageRequest = {
  page: number;          // or `cursor` for keyset pagination on large/volatile tables
  pageSize: 10 | 25 | 50 | 100;
  sort?: `${SortableField}:${'asc' | 'desc'}`[];
  filters?: Partial<Record<FilterableField, string>>;
  q?: string;
};
type PagedResult<T> = { items: T[]; totalCount: number | null; nextCursor?: string | null };
```

- الفرز والفلترة بقائمة حقول مسموحة في .NET، لا أسماء أعمدة حرة تصل إلى SQL.
- `totalCount` مكلف على جداول ضخمة: اجعله اختياريًا أو تقريبيًا، واستخدم keyset للتمرير العميق.
- ترتيب حتمي دائمًا (أضف المفتاح كفرز ثانوي) وإلا تتكرر الصفوف أو تختفي بين الصفحات.
- الحالة كلها في URL (page/sort/filters) ومن ثم في query key.

## حالة الجدول وملكيتها

| الحالة | المالك |
| --- | --- |
| page/sort/filters | URL ← query key، والجدول في وضع manual (`manualPagination/Sorting/Filtering`) |
| التحديد | حالة مكون، بمفتاح صف ثابت (`getRowId: row => row.id`) لا index |
| ظهور/ترتيب/عرض الأعمدة | تفضيل مستخدم: localStorage بإصدار للـschema، أو API تفضيلات |
| التحرير داخل الصف | مسودة لكل صف أثناء التحرير فقط، مع ETag الصف |

## التحديد والإجراءات الجماعية

- عرّف معنى "تحديد الكل": الصفحة الحالية، أم كل النتائج المطابقة للفلتر؟ الثاني يُرسل الفلتر للخادم
  لا آلاف المعرفات، ويعرض العدد قبل التأكيد.
- امسح التحديد عند تغيير الفلتر أو اعرض بوضوح أن عناصر خارج النتائج محددة.
- الإجراء الجماعي يعيد **نتيجة لكل عنصر** (نجح/رفض بسبب/تعارض)؛ اعرض الملخص والتفاصيل، ولا تعلن نجاحًا
  كليًا لنتيجة جزئية. العمليات الطويلة تصبح job مع حالة (راجع مرجع الأعمال الخلفية).
- صلاحية كل إجراء لكل صف من `allowedActions` في الصف؛ عطّل الإجراء الجماعي مع سبب عندما لا ينطبق على
  التحديد، والخادم يتحقق لكل عنصر.

## التصدير

صدّر في الخادم كـjob للأحجام الكبيرة بنفس الفلتر والتفويض، مع حماية من حقن الصيغ في CSV/Excel،
وأعد رابط تنزيل مفوّض. التصدير من الواجهة مقبول للصفحة المعروضة الصغيرة فقط.

## الأداء

- قِس أولًا. صفحة 25–100 صف لا تحتاج virtualization.
- Virtualization (TanStack Virtual) للقوائم الطويلة المحمّلة فعلًا: يكسر Ctrl+F في المتصفح والطباعة
  وقد يربك قارئ الشاشة؛ حافظ على `aria-rowcount`/`aria-rowindex` في نمط grid، وعلى focus عند التمرير.
- خلايا مكلفة: مكونات خلية مستقرة (لا تعريف مكون داخل render)، و`columns` في `useMemo` أو خارج المكون.
- لا تعِد بناء الأعمدة عند كل render؛ تغيّر هويتها يعيد حساب الجدول.

## الإتاحة

- جدول عرض: `<table>` مع `<caption>` و`<th scope>`، وأزرار فرز داخل الترويسة مع `aria-sort`.
- نمط `role="grid"` فقط عند تنقل خلية بخلية بالأسهم (تعديل داخل الخلايا)، مع roving tabindex كامل؛
  لا تضف grid لجدول عرض.
- مربعات التحديد بأسماء ("تحديد طلب 1042")، وإعلان عدد المحدد في live region مهذب.
- الجداول الواسعة: تمرير أفقي داخل حاوية مع `tabIndex={0}` واسم، لا overflow للصفحة. في RTL راجع
  اتجاه التمرير والأعمدة المثبتة.

## الحالات

loading أولي (skeleton بأبعاد الجدول)، تحديث خلفي (مؤشر صغير مع إبقاء الصفوف و`keepPreviousData`)،
فارغ بلا فلتر، فارغ بسبب فلتر (مع زر مسح الفلاتر)، خطأ مع إعادة المحاولة وtraceId، صلاحية غير كافية.

## اختبر

فرز وصفحة في URL وreload، تحديد عبر صفحات، إجراء جماعي بنتيجة جزئية، صف بلا صلاحية للإجراء،
فلتر يعيد الصفحة إلى 1، كتابة سريعة في البحث لا تعرض نتيجة قديمة، تنقل لوحة المفاتيح في الترويسة.
