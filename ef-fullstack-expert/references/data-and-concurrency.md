# البيانات والتزامن

لتصميم schema أو ERD أو مراجعة التطبيع وقاموس البيانات، اقرأ مرجع
database-modeling-and-design من الفهرس. لتصميم فهارس أو تحليل خطة/بطء،
اقرأ database-indexes-and-query-plans. استخدم هذا المرجع لضمانات الوصول
والتزامن والمعاملات وتطور البيانات، دون تكرار التصميم في مصادر متعارضة.

## صمم نموذجًا يحمي قواعد الأعمال

حدد الهوية والعلاقات والكاردينالية وnullability والقيود الفريدة وFK
وسلوك الحذف. عرّف precision/scale للأموال، والوحدات والنطاقات، وثقافة
البحث وترتيب النصوص العربية. لا تعتمد على فحص وجود السجل في الواجهة
لضمان uniqueness؛ ضع constraint مناسبًا في قاعدة البيانات.

ميز بين وقت حدث (غالبًا UTC/DateTimeOffset) وتاريخ أعمال (DateOnly عند
دعمه) وموعد مرتبط بمنطقة زمنية. احتفظ بمعنى المنطقة عندما يحتاجه العمل؛
لا تطبق تحويل UTC على كل تاريخ بصورة عمياء.

طبّق نطاق tenant/workspace/department بحسب الصلاحيات الفعلية. طبّق
النطاق على البحث والعدّ والتصدير والمهام الخلفية، وليس صفحة العرض فقط.
حدد retention والأرشفة وsoft delete وآثاره على uniqueness والعلاقات
عندما تفرضها متطلبات المشروع.

## اختر أسلوب الوصول للبيانات

عند اختيار Dapper أو دمجه مع EF اقرأ dapper-and-sqlclient من الفهرس؛
حدد ownership للاتصال وreader والمعاملة وإعادة المحاولة قبل كتابة SQL.

- استخدم EF Core عندما يلائم التتبع والعلاقات والمعاملات والإنتاجية؛
  راجع توافق provider مع إصدار EF المستهدف.
- قيّم SQL/Dapper لمسار يحتاج تحكمًا في الاستعلام أو تكاملًا قائمًا؛
  لا تفترض تفوقًا عامًا في الأداء دون قياس المسار.
- استخدم parameterization؛ اسمح بفرز ديناميكي عبر قائمة حقول معتمدة،
  ولا تدمج أسماء أعمدة أو أجزاء SQL غير موثوقة.
- نفذ filtering/sorting/projection/pagination في الخادم. حدد حجمًا
  أقصى للصفحة وترتيبًا حتميًا بمفتاح فريد إضافي عند الحاجة.
- راجع N+1 وcartesian explosion والـtracking والـIncludes والاستعلامات
  المنفذة فعليًا. استخدم AsNoTracking للقراءة حين يناسبها؛ لا تحمل جدولًا
  كاملًا إلى الذاكرة ثم تطبق البحث والتصفية.
- اختر offset أو keyset pagination وفق احتياج التنقل والحجم والتغييرات.
  راجع خطة التنفيذ والفهارس باستعلامات وبيانات ممثلة.

## عالج التزامن والمعاملات صراحةً

القراءة ثم الفحص ثم الحفظ وحدها لا تضمن invariant عند طلبين متزامنين.
اختر constraint أو conditional update أو isolation/locking مناسبًا،
واختبر السلوك باستخدام provider الحقيقي.

للتعديل المتفائل، عرّف version/ETag في عقد القراءة والكتابة. يجب أن
يُقارن الحفظ بالنسخة التي عدلها العميل: في EF مثلًا اضبط OriginalValue
لقيمة concurrency token المرسلة بعد التحقق من صيغتها، أو استخدم شرطًا
مكافئًا في UPDATE. المقارنة مع آخر نسخة قُرئت من قاعدة البيانات فقط قد
تسمح بطمس تعديل مستخدم آخر. أعد التعارض المتفق عليه (مثل 409 أو 412
لعقد If-Match)، وامنح العميل فرصة إعادة التحميل أو الدمج.

افحص أيضًا حفظ قيم لم تتغير: قد لا يرسل ORM أي UPDATE، فلا يُفحص
شرط النسخة في قاعدة البيانات. حدد سلوك no-op وفق عقد العملية، واضمن
فحص precondition المطلوبة حتى لهذه الحالة دون ادعاء نجاح حفظ نسخة قديمة.

راع اختلاف providers: SQL Server rowversion ليس timestamp زمنيًا،
وليس آلية عامة في كل قاعدة. ميز DbUpdateConcurrencyException عن مخالفة
unique constraint؛ لا تعالج كل خطأ تخزين باعتباره تعارض نسخة.

حدد حدود المعاملة. لا تمدد معاملة قاعدة البيانات عبر انتظار خدمة
خارجية طويلة. نسق execution strategy مع المعاملات اليدوية حسب provider،
واحسب أثر إعادة المحاولة على العمليات الخارجية.

للعمليات التي يمكن تكرارها، اربط idempotency key بصاحب الطلب والعملية
وبصمة المدخلات، وخزن النتيجة/الحالة مع قيد فريد ومعاملة مناسبة. حدد
سلوك مفتاح مكرر ببيانات مختلفة، وطلبات قيد التنفيذ، وفترة الاحتفاظ.
لا تقدم ضمان exactly-once عامًّا عبر الشبكة.

إذا كان نجاح الحفظ يتطلب نشر رسالة موثوقة، قيّم transactional outbox
ومستهلكًا يتحمل التكرار. صمم التعويض عند العمليات متعددة الأنظمة وفق
قواعد الأعمال، دون إدخال broker إذا لم تحتجه.

## رحّل البيانات دون افتراض بيئة فارغة

افحص migrations والبيانات القائمة قبل التعديل. راجع SQL الناتج وحجم
القفل وزمن التنفيذ. للتغيير الكسري قيّم expand–migrate–contract،
وbackfill وتوافق الإصدارات المتزامنة وخطة فشل أو استرجاع واقعية.

لا تنفذ migration إنتاجية تلقائيًا عند startup أو تحذف/تعيد إنشاء
قاعدة البيانات لتسهيل الاختبار. استخدم نسخة اختبار أو قاعدة معزولة.
راجع ترحيل البيانات القائمة واختبار البدء من قاعدة فارغة عندما يلزمان.

المراجع الرسمية: [EF Core](https://learn.microsoft.com/en-us/ef/core/)،
[Concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency).
اقرأ الصفحة الموافقة للإصدار وprovider عند التنفيذ.

لنشر رسائل موثوقة وinbox والترتيب والـDLQ اقرأ messaging-and-consistency،
ولعزل المستأجرين اقرأ multi-tenancy-design من فهرس المهارة.
