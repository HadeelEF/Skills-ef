# SLOs والإنذار وخطوط CI/CD

اقرأ عند تصميم الرصد والإنذار لنظام إنتاجي، أو إعداد خط بناء ونشر، أو تحديد
معايير «جاهز للإنتاج». السجلات وحدها لا تكشف العطل قبل المستخدم.

## SLI وSLO

- عرّف SLIs للرحلات الحرجة من منظور المستخدم: نسبة الطلبات الناجحة، ونسبة
  الطلبات تحت حد زمني (p95/p99)، وعمر المهام والرسائل المعلقة، وحداثة البيانات.
- SLO هدف متفق عليه مع المالك (مثلًا 99.5% من طلبات الاعتماد تنجح خلال 30
  يومًا). لا تخترعه؛ اقترح قيمة موسومة كمقترح واطلب اعتمادها.
- error budget = 100% − SLO. استهلاكه السريع يبرر إيقاف الإصدارات المحفوفة بالمخاطر.

## الإنذار

- أنذر على أعراض يشعر بها المستخدم أو تقترب منه: معدل 5xx، تجاوز latency، معدل
  حرق error budget، عمر أقدم رسالة outbox/job، فشل تجديد شهادة قبل انتهائها،
  امتلاء القرص، فشل backup.
- كل إنذار له: شدة، مالك، رابط runbook، ولوحة تبدأ منها. إنذار بلا إجراء = ضجيج.
- لا تنذر على كل استثناء أو CPU لحظي. استخدم نوافذ زمنية وعتبات مستقرة.
- لوحات: RED للخدمات (Rate، Errors، Duration) وUSE للموارد (Utilization،
  Saturation، Errors)، مع طبقة DB (Query Store، waits، blocking) والـpools والطوابير.
- مقاييس منخفضة cardinality؛ لا userId أو URL بمعرفات كـlabel.

## خط CI

1. restore بـlock files، وbuild بـwarnings as errors للمشاريع الجديدة.
2. analyzers وتنسيق، وفحص الاعتماديات المعرضة للثغرات (مثل
   `dotnet list package --vulnerable` أو أداة المؤسسة)، وفحص الأسرار.
3. unit tests، ثم integration tests على SQL Server حقيقي (container أو بيئة معزولة).
4. OpenAPI diff للتغييرات الكاسرة، وتوليد migration script ومراجعته.
5. نشر artifact واحد موسوم بالإصدار والـcommit؛ لا إعادة بناء لكل بيئة.

## خط CD

- رقِّ نفس الـartifact بين Dev → Test → UAT → Prod مع config خارجي لكل بيئة.
- خطوات الإنتاج: موافقة، نافذة نشر، migration مخولة منفصلة (expand أولًا)، نشر
  بالتدريج أو blue/green، فحص readiness ورحلة smoke حقيقية، مراقبة إشارات محددة
  لفترة محددة، ثم إعلان النجاح.
- معايير rollback مكتوبة مسبقًا (مثل ارتفاع 5xx فوق خط الأساس) لا قرار لحظي.
- contract migration (حذف عمود قديم) في إصدار لاحق بعد التأكد من خروج N-1.

## الجاهزية للإنتاج

قبل الإطلاق: SLOs وإنذارات بمالكين، runbooks للأعطال الشائعة، backup واستعادة
مجربة، اختبار حمل للذروة المتوقعة، مصفوفة فشل مختبرة لأهم الاعتماديات، تدوير
الأسرار والشهادات موثق، وخطة rollback مجربة مرة واحدة على الأقل.

## التشخيص من الـtelemetry بدل التخمين

1. ابدأ من الإشارة: أي SLI تدهور، متى بالضبط، لأي endpoint أو مستأجر أو نسخة.
2. قارن نافذة العطل بنافذة سليمة: توزيع latency، معدل الأخطاء، الاعتماديات في traces.
3. افتح traces بطيئة ممثلة: أين يذهب الزمن (DB، HTTP خارجي، انتظار lock/pool، التطبيق)؟
4. اربط بالمقاييس على مستوى المورد: ThreadPool queue، اتصالات DB، waits في SQL،
   GC pause، طوابير الرسائل.
5. ارجع إلى السجلات بالـtraceId للتفاصيل، لا العكس.
6. صُغ فرضية واحدة، واختبرها بإشارة يمكن أن تنفيها، ثم قرر التخفيف.

إذا لم تكفِ الـtelemetry لهذا المسار فذلك بحد ذاته إجراء في الـpostmortem.
