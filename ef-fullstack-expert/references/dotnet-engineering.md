# هندسة C# وASP.NET Core

## وافق البيئة والإصدار

افحص global.json وTargetFramework وLangVersion وNullable وSDK المثبت
وتوافق الحزم والاستضافة. راجع API في وثائق الإصدار المستهدف. استخدم
ميزات C# التي تحسن الوضوح وتدعمها سلسلة البناء. لا تستنتج إصدار runtime
من رقم SDK، ولا ترقّ المشروع كأثر جانبي لإصلاح محدود.

## اكتب C# يحافظ على المعنى

- عبّر عن invariants بالأنواع والتحقق. استخدم nullable reference types
  واتفاقيات واضحة؛ لا تسكت التحذيرات بـ ! دون حجة.
- افصل DTOs العامة عن entities وامنع mass assignment. استخدم mapping
  صريحًا عندما يكفي؛ اختبر التحويلات المؤثرة في مبالغ أو صلاحيات.
- حدد مقارنة النصوص والتواريخ والثقافة عند أهميتها. استخدم decimal
  للأموال مع دقة العملة وقواعد التقريب المعتمدة.
- استخدم async من البداية إلى النهاية لعمليات I/O. مرر CancellationToken
  إلى EF/HTTP والعمليات الداعمة له؛ تجنب .Result و.Wait وasync void
  وTask.Run لتغليف I/O غير متزامن أصلًا.
- لا تنفذ عمليات متوازية على DbContext واحد. استخدم سياقات مستقلة فقط
  عندما يكون ذلك صحيحًا للمعاملة ومنضبطًا لاتصالات قاعدة البيانات.
- احترم IDisposable/IAsyncDisposable وملكية الموارد. عالج الاستثناء
  عند المستوى الذي يملك سياسة الاستجابة؛ حافظ على stack trace.

## ابنِ خط طلب واضحًا

اختر Minimal APIs أو Controllers وفق اتفاقيات المشروع والحالات والأدوات.
قسم endpoints إلى ملفات أو مجموعات مفهومة؛ تجنب تكديس قواعد العمل
وتفاصيل قاعدة البيانات في Program.cs.

رتب middleware حسب توثيق الإصدار والتطبيق: معالجة الأخطاء، والـproxy
الموثوق، وHTTPS/CORS والمصادقة والتفويض. اضبط forwarded headers
للـproxies المعروفة فقط. لا تحل مشكلة CORS بتوسيع غير مقيد.

استخدم DI بأعمار صحيحة. تجنب service locator وBuildServiceProvider
أثناء التسجيل وحقن scoped داخل singleton. أنشئ scope داخل background
worker عند الحاجة، وراع الإلغاء والإغلاق المنظم.

تحقق من options المطلوبة عند البدء، واستخدم configuration حسب البيئة.
احفظ الأسرار خارج appsettings المتعقب والكود والاستثناءات والسجلات.

## تحقق وأعد استجابات متسقة

افصل أخطاء صيغة الطلب عن قواعد العمل وتعارض البيانات. راجع دعم
validation الفعلي في نوع endpoints وإصدار ASP.NET Core؛ لا تفترض
سلوك Controllers متاحًا تلقائيًا في Minimal APIs.

استخدم ProblemDetails أو عقد الأخطاء المعتمد بمفاتيح مفهومة وtrace ID
آمن. أعد status مناسبًا؛ لا تحول جميع الأخطاء إلى 200 أو 500. لا تعرض
stack traces أو تفاصيل SQL أو بيانات حساسة للعميل.

استخدم System.Text.Json وإعداداته المدعومة عند كفايته. عرّف سلوك enums
والتاريخ والحقول الاختيارية وتوافق العقود. لا تسلسل graph من entities
بما ينتج دورات أو تحميلًا غير مقصود أو كشف بيانات.

## أدر المهام والتكاملات

للعمل المرتبط بالطلب، انتظر اكتماله. للعمل المؤجل عرّف قبول الطلب
وحالته وتخزينه وإعادة المحاولة ثم اختر worker أو scheduler مناسبًا.
لا تستخدم fire-and-forget داخل الطلب لضمان عملية يجب ألا تضيع.

أدر عمر HttpClient واستخدم typed/named clients عند ملاءمتها. حدد
timeout وcancellation وretries وbackoff وحدود التوازي. راجع أمان
إعادة المحاولة قبل تكرار POST أو تأثير خارجي.

قيّم SignalR لحاجة realtime، وgRPC لاتصال وعقد مناسبين، وAspire لفائدة
في تنسيق التشغيل المحلي والخدمات. راجع قيود trimming وNative AOT
والتسلسل والاعتماديات قبل اختيارها. أضف التقنيات بحسب الحاجة المثبتة.

## شخّص قبل التحسين

ابدأ بدليل: زمن الطلب، traces، SQL، CPU، allocations، أو saturation
في thread/connection pools. أصلح الاستعلام والـI/O غير المحدودين أولًا.
قارن قبل/بعد بعبء ممثل وبيانات وطريقة قياس معلنة؛ لا تنسب benchmark
خارجيًا إلى بيئة المستخدم.

للتعمق في allocations وGC وasync internals وأدوات التزامن اقرأ
dotnet-runtime-and-concurrency من فهرس المهارة.
