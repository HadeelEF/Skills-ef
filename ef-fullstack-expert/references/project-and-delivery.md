# فهم المشروع وإكمال التنفيذ

## اجمع الأدلة المناسبة

- افحص تعليمات العمل وحالة Git. احفظ التعديلات الموجودة ولا تعيد ضبطها
  أو تستبدلها. حدد الفروع والمسارات التي تدخل ضمن المهمة.
- اقرأ المتطلبات المعنية، وخرائط الحل، وملفات المشاريع والاعتماديات
  والقفل، وتهيئة التشغيل وCI والاختبارات ذات الصلة. لا تطبع الأسرار.
- تتبع رحلة فعلية: route في الواجهة، ثم عقد API، ثم authorization،
  ثم use case، ثم الاستعلام أو المعاملة، ثم الاستجابة المعروضة للمستخدم.
- سجل مصدر الحقيقة لكل جانب: الوثيقة المعتمدة للسلوك المستهدف، والكود
  للسلوك المنفذ، والاختبار للسلوك المتحقق. أظهر اختلافها بدل طمسه.
- عند مراجعة شاملة أنشئ خريطة تغطية للوحدات المهمة. لا تقل إنك قرأت
  كل المستودع إذا لم تفعل. التغيير المحدود يستلزم قراءة نطاقه واعتمادياته.

## حدد النطاق حسب الطلب

في مشروع جديد، احسم المستخدمين والوظائف الأساسية والحجم المتوقع
ومتطلبات الأمان والتوافر والبيانات والاستضافة وقدرة الفريق التشغيلية.
عند نقص معلومات غير مانعة، استخدم افتراضًا صريحًا يمكن تغييره.

في ميزة جديدة، صغ معايير قبول تشمل النجاح، والمدخل غير الصحيح، والوصول
غير المصرح، وفشل الاعتماديات. أضف التزامن أو تكرار الطلب عندما يؤثران
في صحة البيانات. في الإصلاح، أعد إنتاج المشكلة بأصغر حالة متاحة، أو
تتبع دليلها إن لم تتوفر بيئة التشغيل؛ أصلح السبب واختبر السلوك المتأثر.

## نفّذ على مراحل قابلة للتشغيل

1. ثبت baseline: أوامر البناء والاختبار والمشكلات الموجودة.
2. حدد عقد API وشكل البيانات والصلاحية قبل ربط الأطراف.
   حدد ملفات الميزة ومسؤولياتها واتجاه dependencies ومالك الحالة؛
   استخدم naming/configuration القائمين، ولا تنشئ هيكلًا غير مستخدم.
3. أنجز use case ممثلًا بقواعد أعمال وحفظ حقيقي ضمن نطاق التنفيذ.
4. اربط الواجهة أو العميل وافحص النجاح والفشل واستمرار البيانات.
5. وسّع النمط الذي أثبت ملاءمته، ثم نفذ الاختبارات اللازمة للتغيير.
6. راجع diff: لا تعديلات عارضة أو أسرار أو placeholders تمنع المسار
   المطلوب أو واجهة تقول «تم» قبل اكتمال العملية.

عند طلب معمارية كود، اربط قرار التنظيم بمسارات ومسؤوليات وpublic contracts
ومسار use case ممثل. وعند طلب تنفيذها، حدّث الملفات والتسجيلات والمستهلكين
والفحوص؛ الرسم أو tree وحدهما لا يكملان إعادة الهيكلة.

عند غياب خدمة أو صلاحية، اجعل حدود المحاكاة ظاهرة. استخدم عقد تكامل
واضحًا وقابلية حقن للاختبار؛ لا تقدم mock على أنه تكامل إنتاجي.

## أدر العقبات والتسليم

- جرّب البديل الآمن المتاح قبل التوقف. احترم قيود الوصول وتعليمات المشروع.
- إذا غاب SDK أو مصدر حزم أو قاعدة بيانات، أكمل الأجزاء المستقلة، وافصل
  «الكود مكتوب/مراجع» عن «تم البناء/التشغيل». اذكر الأمر الذي تعذر وأثره.
- احترم نطاق المستخدم: الاستشارة لا تستلزم تعديل الملفات؛ والتنفيذ
  المصرح لا يستلزم موافقات متكررة للتفاصيل المعتادة القابلة للعكس.
- اربط النتيجة بمعايير القبول. أعط أمر التشغيل أو الاختبار الفعلي، وأي
  migration أو configuration يحتاجه من يكمل العمل.
