اقرأ عند Database Design أو ERD أو تصميم schema جديدة أو مراجعة نموذج
قائم. اجمعه مع مرجع البيانات والتزامن، ونمذجة EF، والفهارس عند الحاجة.
ابدأ من قواعد المجال والاستعلامات والبيانات القائمة، لا من DTOs أو شكل
الشاشة وحدهما. احترم محرك المشروع وملكية schema وقيود الاستضافة.

## افصل المفهومي والمنطقي والفيزيائي

| المستوى | ما تحدده | معيار المراجعة |
| --- | --- | --- |
| Conceptual | المصطلحات والكيانات والعلاقات والملكية وأحداث الأعمال | يمثل المجال والمستخدمين دون افتراض جداول لكل شاشة |
| Logical | attributes، candidate keys، cardinality/optionality، قواعد التكامل والتطبيع | يمكن تفسير مصدر كل حقيقة وعلاقة وقيد |
| Physical | جداول وأعمدة وأنواع وPK/FK/UNIQUE/CHECK وفهارس وسلوك حذف | متوافق مع المحرك ومطبق فعليًا في DDL/EF |

قدر الحجم والنمو وتوزيع البيانات ونسبة القراءة للكتابة وأهم الاستعلامات
بافتراضات معلنة؛ لا تحول تقديرًا إلى قدرة مثبتة. ميز OLTP عن نموذج تقارير
أو analytics، وحدد مصدر الحقيقة وحداثة النسخ المشتقة. لا تفرض star schema
على المعاملات أو نسخ بيانات إلى DW لمجرد وجود تقارير بسيطة.

## صمم العلاقات والاعتماديات

- حدد لكل علاقة 1:1 أو 1:N أو M:N، وهل الطرف اختياري، ومن يملك دورة
  حياتها. علاقة 1:1 تحتاج uniqueness مناسبة، لا FK فقط. لربط M:N استخدم
  جدول ربط واضحًا، وضع فيه خصائص العلاقة وفترة صلاحيتها إن وجدت.
- اختر PK ثابتًا مناسبًا، واحتفظ بالـbusiness key كقيد مستقل بنطاقه.
  ناقش surrogate مقابل natural/composite، وعرض المفتاح وآثاره على FK
  والتخزين. نوع ID أو كونه PK لا يحدد وحده اختيار clustered index.
- صمم الرقم التجاري وتوليده ونطاق uniqueness؛ لا تستخدم MAX+1 بلا
  حماية تنافس. وضح هل يسمح المجال بفجوات التسلسل، دون وعد sequence بلا فجوات.
- راجع functional dependencies وتكرار الحقائق: أزل المجموعات المتكررة
  والاعتماد الجزئي على composite key والاعتماد المتعدي غير المقصود.
  استخدم 1NF/2NF/3NF أساسًا للفحص حيث تلائم النموذج، مع تفسير القرار.
- لا تخزن IDs مترابطة في CSV أو تجعل JSON/EAV بديلًا افتراضيًا للعلاقات.
  JSON مناسب لبيانات مرنة محددة الملكية؛ حدد validation وإمكان الاستعلام
  والفهرسة والترقية، وما الذي لن تستطيع FK/constraints حمايته داخله.
- برر denormalization بمسار قراءة وتكلفة مثبتة أو متطلب تاريخي. حدد
  المصدر ومالك التحديث وtransaction/reconciliation واختبار الاتساق.
  snapshot سعر أو وصف معتمد وقت العملية يختلف عن تكرار مرجع حالي بالخطأ.
- ميز current state وbusiness revisions وtemporal history وaudit trail؛
  سجل نسخ الصف لا يشرح تلقائيًا من فعل ماذا ولماذا، ولا يعوض عقد التدقيق.

## اختر الأنواع والقيود وفق المعنى

- حدد طول النص وUnicode/collation وقواعد مساواة وبحث وترتيب العربية.
  اختبر أثر case/accent/التطبيع على uniqueness؛ احفظ الأصل، ولا تغير
  أسماء الأشخاص أو الهمزات تلقائيًا تحت مسمى «تنظيف البيانات».
- اختر decimal precision/scale والعملة والوحدة وسياسة التقريب بحسب
  المجال. افصل nullable عن قيمة صفرية. وثق date-only مقابل instant
  والمنطقة الزمنية عند الحاجة، ونوع التخزين والتسلسل المقابلين في .NET.
- احم حدود JSON/JavaScript: bigint ومعرفات طويلة وdecimal قد لا تحفظ
  دقتها في number. اختر عقد نقل يحفظ المعنى، وطبقه في DTO وTypeScript
  وform parsing دون تحويل صامت يفقد أرقامًا أو يوم أعمال.
- طبق NOT NULL وCHECK وUNIQUE وFK حيث يناسب الضمان. في SQL Server
  CHECK بشرط موجب لا يمنع NULL وحده؛ default لا يبدل NULL المرسلة صراحةً.
  لا تعد بأن CHECK على صف يحمي مجموع صفوف أو انتقالًا متزامنًا معقدًا.
- حدد سلوك NULL في unique/composite keys وفق المحرك والإصدار؛ لا تنقل
  افتراضات SQL Server إلى PostgreSQL. للـsoft delete حدد إعادة استخدام
  الكود وسياسة active uniqueness، وراجع دعم filtered/partial indexes.
- سمّ القيود والفهارس باتفاقيات واضحة لتسهيل التشخيص والهجرة. راجع
  cascade/restrict/set-null وفق دورة الحياة الفعلية؛ لا تجعل حذف parent
  يمحو تاريخ أعمال مطلوبًا أو يترك orphan، واختبر السلوك على provider الحقيقي.

## احم النطاق ودورة حياة البيانات

في multi-tenant/workspace model حدد scope لكل جدول وعلاقة وقيد. FK
على ProjectId وحده لا يثبت أن TenantId في child يطابق tenant في parent.
عند اشتراط هذا التطابق استخدم علاقة مركبة مثل (TenantId, ProjectId)
إلى candidate key مناسبة (TenantId, Id)، أو تصميمًا يضمن النطاق دون
تكرار غير محمي. نسق alternate/composite keys مع EF configuration.

راجع nullable composite FKs وما إذا كان غياب جزء منها يسقط فحص العلاقة،
ومنع الحالة الجزئية إن كانت غير مسموحة. ميز الجداول المشتركة عالميًا
عن بيانات المستأجر. query filters وRLS إن استُخدما يحتاجان سياقًا صحيحًا
واختبارات bypass/pooling؛ القيود المرجعية لا تستبدل resource authorization.

حدد البيانات الحساسة ومصدرها ومالكها والاحتفاظ والأرشفة والحذف، وصلاحيات
حساب التطبيق مقابل حساب تغيير schema. اربط تشفير الأسرار/المفاتيح
واستعادة النسخ الاحتياطية بسياسة البيئة الفعلية؛ لا تخلط soft delete
بالمحو النهائي أو تعتبر وجود backup دليلًا على نجاح restore.

## اجعل التصميم قابلًا للتنفيذ والمراجعة

للتصميم المؤثر سلّم المخرجات الملائمة التالية متطابقة، وادمجها في وثائق
المشروع بدل تكرارها. لإضافة عمود صغيرة يكفي تحديث الأجزاء المتأثرة:

| المخرج | المحتوى المطلوب |
| --- | --- |
| ERD | أسماء موحدة، PK/FK، cardinality وoptionality وحدود النطاق |
| Data dictionary | معنى الحقل، النوع/الطول/الدقة، nullable/default، المفاتيح والقيود، المصدر والحساسية |
| Constraint catalog | القاعدة، نطاقها، موضع فرضها، سلوك الفشل، والتحقق تحت التزامن |
| Query/index map | الاستعلامات المهمة والفهارس المرشحة وسبب ترتيب أعمدتها وكلفتها |
| التنفيذ | DDL أو EF mappings/migration حسب ملكية schema، وعقود API وواجهة متوافقة |
| الترحيل والتحقق | تنظيف/backfill مبرر، توافق الإصدارات، اختبارات DB جديدة وupgrade لبيانات قائمة |

راجع ERD والقاموس والكود وSQL الناتج معًا؛ FK مرسومة وغير منشأة ليست
ضمانًا. اختبر التكرار والقيم الحدية والـNULL والحذف والعلاقة العابرة
للنطاق، ثم السيناريو المتزامن الذي يهدد القاعدة. صف التصميم المقترح
والقيود المنفذة وما جرى تشغيله كلًا بدقة؛ لا تسم فحصًا نصيًا اختبار DB.

في backfill تاريخي استخدم وثائق أو سجلات موثوقة، وحدد البيانات التي لا
يمكن استعادتها. لا تملأ snapshot قديمة بقيمة المرجع الحالية ثم تصفها
بأنها الحقيقة وقت الاعتماد؛ اتفق على معالجة معلنة لما لا يملكه المصدر.
