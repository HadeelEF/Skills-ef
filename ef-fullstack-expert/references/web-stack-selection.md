# اختيار تقنيات الويب

## اختر تركيبًا متناسقًا للمشروع

افحص ملفات .csproj وPages وViews وControllers وwwwroot و_Layout.cshtml
وpackage.json وlibman.json وlockfiles وخط CI قبل القرار. تحقق من النسخ
الفعلية لملفات vendor أو CDN في layout؛ قد تختلف عن اسم قالب المشروع.

| الحالة | خيار مناسب للتقييم | ما يجب حسمه |
| --- | --- | --- |
| تطبيق صفحات ونماذج وسير عمل مع تفاعل موضعي | ASP.NET Core Razor Pages مع HTML وCSS وJavaScript | PageModels وحدود خدمات الأعمال والنماذج والمصادقة |
| تطبيق MVC قائم أو تنظيم controllers/views مطلوب | ASP.NET Core MVC وRazor views | actions وview models وتوليد المسارات وإعادة استخدام العرض |
| شاشة بسيطة أو موقع ثابت أو تحسين تفاعل محلي | HTML وCSS وJavaScript بحسب الخادم القائم | ما يعمل دون JS، ومتى تحتاج API |
| واجهة غنية بحالة وتفاعلات مستمرة ومكونات مترابطة | React/TypeScript مع ASP.NET Core API | عقود البيانات والهوية والحالة وخطوط البناء والنشر |
| مشروع يعتمد jQuery وإضافاته | تحسين تدريجي داخل النمط القائم | توافق plugins وAJAX ودورة حياة DOM، وخطة ترقية إن طُلبت |
| جزء React داخل صفحات Razor موجودة | جزر تفاعلية معزولة عند وجود فائدة | mount/unmount، بيانات البدء، asset loading، وحدود ملكية DOM |

Razor Pages وRazor views يستخدمان .cshtml. ملفات .razor تخص مكونات
Blazor ذات نموذج تشغيل مختلف. تحقق من النوع قبل اقتراح lifecycle
أو event binding. لا تقدم كود Blazor بدل Razor Pages.

## اربط الخادم بالعرض بوضوح

PageModel أو controller ينسق مع use cases/services ويفرض الوصول للمورد؛
الـview يعرض البيانات. يمكن أن تتشارك صفحة وAPI في خدمة أعمال دون
استدعاء loopback HTTP بينهما. استخدم HTTP عندما توجد حدود خدمة حقيقية.

اختر handler لعملية مرتبطة بصفحة وعقدها عندما يكفي. اختر API مستقلة
عند تعدد العملاء أو الحاجة إلى عقد JSON قابل للتطور. لا تكرر قواعد
الأعمال بين handler وcontroller والعميل؛ يملك الخادم مصدر الحقيقة.

اتفق على نتيجة الطلب: HTML كامل أو partial موثوق أو JSON، وعلى الفشل
والدخول المنتهي. التحسين عبر AJAX يحافظ على معنى العملية وقيودها؛ ليس
مبررًا لتعطيل CSRF أو الصلاحيات.

## اختر أساس التصميم

CSS عادي مناسب لتصميم محدود أو نظام تصميم قائم؛ Bootstrap يفيد عندما
تلائم مكوناته وأنماطه المشروع؛ Tailwind يفيد في بناء مكونات وتصميم
مخصص. اجعل هوية EF المرجع للألوان والخطوط والمقاسات، واختبر الإتاحة
والتجاوب مهما كان الخيار. لا يحدد إطار CSS تقنية الخادم أو الواجهة.

استخدم أساسًا واحدًا افتراضيًا للصفحة. عند وجود Tailwind وBootstrap
معًا، حدد خطة عزل/انتقال ومَن يملك resets وutilities والمكونات وترتيب
تحميل CSS. قيّم أثر Preflight وReboot وتسميات مثل container وcollapse.

## صمم بناءً ونشرًا يمكن تكرارهما

فرق بين أدوات وقت البناء وruntime الإنتاج. قد تحتاج Razor إلى Node
لبناء Tailwind أو JavaScript، دون احتياج خادم Node في التشغيل. ضمن
نسخ assets الناتجة إلى wwwroot ومخرجات dotnet publish، وفحص الروابط
والـbase path والـcache busting. حافظ على النسخ المقفلة وخط بناء موحد
محليًا وفي CI. استخدم موارد محلية عندما تمنع البيئة الاتصال الخارجي.

عند تطوير مشروع قائم، قدر تكلفة الترحيل على الوظائف وplugins والاختبارات
والفريق قبل اقتراح استبدال إطار. قدم خطوة تطور يمكن اختبارها وعكسها.
