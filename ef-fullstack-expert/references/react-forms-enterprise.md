# نماذج المؤسسات في React

اقرأ عند بناء نموذج إدخال أو تعديل، أو ربط أخطاء التحقق من ASP.NET Core، أو تحسين أداء نموذج
كبير. الأمثلة لـReact Hook Form v7 وzod v4؛ تحقق من الإصدار. التنفيذ المختبر:
`golden-react-feature/src/features/requests/components/CreateRequestForm.tsx`.

## افصل ثلاثة أشياء

- **المسودة (draft):** ما يكتبه المستخدم الآن. نصوص في الغالب: "1." و"0" و"" قيم مؤقتة مشروعة.
- **الأمر (command):** ما يُرسل للخادم، يُبنى مرة واحدة عند submit بتحويل صريح.
- **لقطة الخادم:** آخر قراءة مؤكدة مع ETag.

لا تحوّل `Partial<Entity>` إلى عقد تعديل؛ عرّف command بالحقول المسموح للمستخدم تعديلها فقط.
لا تحوّل الأرقام أثناء الكتابة (`valueAsNumber` يفقد "1." ويحوّل الفارغ إلى NaN). المبالغ تبقى
نصًا من الحقل إلى JSON إلى decimal في .NET.

## Schema واحد، تحقق في مكانين

- schema zod يغذي `zodResolver` للتحقق الفوري ويعطي النوع (`z.infer`).
- الخادم يبقى المرجع: FluentValidation أو DataAnnotations وقواعد العمل. تحقق الواجهة لتحسين التجربة.
- لا تكرر قواعد العمل المعقدة (الميزانية المتبقية، فصل المهام) في الواجهة؛ اعرض ما يعيده الخادم.
- عند مشاركة القيود البسيطة (طول العنوان) اجعل مصدرها واحدًا: OpenAPI أو ثابت مولّد، وإلا اكتب
  تعليقًا يربطها بالثابت في .NET واختبار عقد يكشف الانحراف.

## اربط ValidationProblemDetails بالحقول

مفاتيح ASP.NET Core ليست مسارات RHF، وتختلف بحسب المصدر:

| المصدر | مثال مفتاح |
| --- | --- |
| DataAnnotations/FluentValidation | `Items[1].UnitPrice` |
| أخطاء JSON binding في System.Text.Json | `$.items[1].unitPrice` |
| خطأ على مستوى النموذج | `""` أو اسم النموذج |

حوّلها: احذف `$.`، و`[n]` إلى `.n`، و camelCase لكل جزء. ثم:

1. `setError(path, { type: 'server', message })` للحقول **المعروضة فعلًا** (صف موجود في field array).
2. كل ما لا يطابق حقلًا ظاهرًا يذهب إلى ملخص أعلى النموذج بـ`role="alert"`؛ لا تُسقط قاعدة خادم.
3. انقل focus إلى أول حقل خاطئ (`setFocus`)، واحتفظ بكل الإدخال.
4. اختبر المفاتيح الفعلية لـAPI باختبار عقد؛ الدالة في المثال الذهبي تغطي الأشكال الشائعة لا كل مشروع.

## Field arrays

- `useFieldArray` و`key={field.id}`؛ لا تستخدم index كمفتاح، ولا `Math.random()`.
- استخدم `append/remove/move/replace` من الـhook؛ لا تعدّل مصفوفة القيم مباشرة.
- اربط أسماء الحقول المتكررة بالرقم في label المرئي أو `aria-label` المجموعة ("سعر الوحدة 2")
  حتى يميزها قارئ الشاشة ويستطيع الاختبار إيجادها بالاسم.
- خطأ المصفوفة نفسها (`min(1)`) يظهر في `errors.items.root` أو `errors.items.message` حسب الإصدار؛
  اعرض الاثنين أو تحقق من موضعه.

## الحقول الشرطية والنماذج متعددة الخطوات

- قرر مصير قيمة الحقل المخفي: `shouldUnregister: true` يحذفها من القيم؛ الافتراضي يبقيها ويرسلها.
  اجعل schema متسقًا (`z.discriminatedUnion` على الحقل الحاكم) حتى لا يُرسل حقل مخفي قديم.
- Wizard: نموذج واحد بعدة خطوات و`trigger([...fieldsOfStep])` قبل الانتقال، أو نماذج منفصلة مع
  مسودة مشتركة. احفظ الخطوة في URL إذا كان الرجوع بالمتصفح متوقعًا.
- المسودات الطويلة: حفظ تلقائي إلى الخادم كمسودة (أفضل) أو sessionStorage بلا بيانات حساسة، مع
  إصدار للـschema حتى لا تُستعاد مسودة بشكل قديم.

## الأداء في النماذج الكبيرة

- RHF غير متحكم افتراضيًا: لا تجعل كل حقل `Controller` إلا للمكونات التي تتطلبه (select مخصص،
  date picker).
- `useWatch({ name })` في مكون صغير بدل `watch()` في الجذر الذي يعيد render النموذج كله.
- `formState` proxy: اقرأ فقط ما تعرضه (`isDirty` يكلف مقارنة مع defaults).
- قوائم خيارات كبيرة: احملها بـquery مع cache لا داخل النموذج، وvirtualize القائمة المنسدلة.
- قِس بـReact Profiler عند الكتابة في حقل قبل أي memo.

## الإرسال وما بعده

- زر submit `disabled` أثناء `isSubmitting`، وحارس في handler؛ والخادم يحمي بـidempotency أو ETag.
- **Idempotency-Key لكل مسودة لا لكل نقرة:** بعد نتيجة مجهولة يعيد المستخدم الإرسال بأمان. جدد المفتاح
  بعد النجاح فقط. يتطلب تخزين النتيجة في الخادم.
- بعد النجاح: `reset(values)` لإزالة dirty، ثم التنقل. لا تعرض نجاحًا قبل استجابة ناجحة.
- **حارس التغييرات غير المحفوظة:** `useBlocker` للتنقل داخل التطبيق مع dialog قابل للوصول؛ اسمح
  للتنقل بعد الحفظ بقراءة ref يضبطه handler النجاح، لأن قيمة `when` الملتقطة قبل re-render قد تحجب
  تنقلك أنت. `beforeunload` لإغلاق التبويب فقط، وغير موثوق على الجوال.
- تعديل مورد موجود: أرسل ETag المسودة الأصلية؛ عند 412 لا تكتب فوق إدخال المستخدم بالبيانات الجديدة
  تلقائيًا: اعرض الفرق أو خيار إعادة التحميل.
- refetch أثناء التحرير: لا تعِد تهيئة النموذج من بيانات أحدث إلا بقرار (`values` مع `resetOptions:
  { keepDirtyValues: true }` أو تنبيه).

## الإتاحة

`label` مرتبط بـ`htmlFor`، و`aria-invalid` عند الخطأ، و`aria-describedby` لرسالة الخطأ والتلميح،
و`autocomplete` و`inputMode` المناسبان، و`noValidate` مع رسائلك بدل فقاعات المتصفح غير المترجمة.
لا تعتمد على اللون وحده للخطأ. الملخص يذكر الأخطاء التي لا ترتبط بحقل.

## اختبر

client validation تمنع الطلب، أخطاء الخادم على الصف الصحيح وfocus إليه، رسالة غير مطابقة تظهر
في الملخص، الإدخال يبقى بعد الفشل، نفس idempotency key بعد نتيجة مجهولة، شكل الأمر المرسل
(decimal نص، لا حقول للقراءة فقط)، حارس التنقل لا يحجب التنقل بعد الحفظ.
