# أخطاء الواجهة ورصدها في الإنتاج

اقرأ عند تصميم معالجة الأخطاء في تطبيق React، أو إعداد الرصد، أو تشخيص أعطال يبلغ عنها
المستخدمون. الرصد في الخادم وOpenTelemetry في مرجع السجلات والمراقبة.

## صنّف قبل أن تعالج

| الفئة | مثال | معاملتها |
| --- | --- | --- |
| حالة منتج متوقعة | 400 تحقق، 404، 409 قاعدة عمل، 412 تعارض | تجربة مستخدم مصممة؛ **لا تُبلّغ كحادث** |
| فشل عابر | network، timeout، 503 | retry محدود للقراءة، رسالة مع إعادة محاولة |
| نتيجة مجهولة | فقد استجابة كتابة | تحقق من الخادم أو idempotency؛ لا "فشل" يقيني |
| انحراف عقد | JSON لا يطابق schema، HTML بدل JSON | خطأ عقد يُبلّغ؛ لا يُعرض كقائمة فارغة |
| خلل برمجي | exception في render أو handler | Error Boundary أو global handler، يُبلّغ مع السياق |

اجعل الفئات أنواعًا (union مميز كما في `apiError.ts` في المثال الذهبي) وعالجها بـswitch شامل.

## طبقات الالتقاط

1. **Error Boundary لكل route** (أو `ErrorBoundary` في router) + boundary عام للـshell: شاشة واحدة معطلة
   لا تسقط التنقل. Boundary في React ما زال class component أو مكتبة مثل `react-error-boundary`.
2. **ما لا تلتقطه boundaries:** handlers، وasync، وtimers. عالجها في مصدرها، وثبّت `window` handlers لـ
   `error` و`unhandledrejection` كشبكة أخيرة.
3. **React 19 root options:** `createRoot(el, { onUncaughtError, onCaughtError, onRecoverableError })`
   لإرسال أخطاء React إلى الرصد مرة واحدة (تحقق من الإصدار).
4. **فشل تحميل chunk بعد نشر جديد:** Vite يطلق حدث `vite:preloadError` على `window`؛ اعرض "تم تحديث
   التطبيق" مع إعادة تحميل، ولا تدخل حلقة reload.

## ما يراه المستخدم

- رسالة بلغة المستخدم تشرح ما حدث وما يفعله، لا نص استثناء ولا title الخادم الإنجليزي.
- **رقم مرجع** هو `traceId` من ProblemDetails (ASP.NET Core يضيفه عند إعداد `AddProblemDetails`)، داخل
  `<bdi dir="ltr">` ليُنسخ صحيحًا في الواجهة العربية. الدعم يبحث به مباشرة في traces الخادم.
- حافظ على إدخال المستخدم في أي خطأ.
- استخدم `role="alert"` للأخطاء التي تتطلب انتباهًا و`role="status"` للنتائج، دون إعلان متكرر لكل render.

## الربط بين الواجهة والخادم

- OpenTelemetry web (`instrumentation-fetch`) يضيف `traceparent` لطلبات API، فتتصل spans المتصفح بالخادم.
  مع أصل مختلف أضف الأصل إلى `propagateTraceHeaderCorsUrls` واسمح بالرأس في CORS. مع BFF نفس الأصل أبسط.
- أرسل مع كل تقرير: إصدار التطبيق (build id)، والـroute بقالبها (`/requests/:id` لا المعرف)، والمتصفح،
  وtraceId إن وجد. لا PII ولا محتوى النماذج ولا tokens؛ نقِّ الرسائل والـURLs قبل الإرسال.
- source maps مخفية تُرفع لأداة الرصد مع كل build.
- خفف التكرار: نفس الخطأ من نفس المستخدم مرة لكل جلسة، وsampling للأحداث الكثيرة.

## RUM والأداء الميداني

اجمع LCP وINP وCLS من المستخدمين الفعليين (مكتبة `web-vitals` مع attribution) مقسمة حسب route
والإصدار، وp75 كمقياس. أضف مقاييس منتج: زمن البحث، وزمن الحفظ. البيانات المختبرية (Lighthouse) لا
تمثل أجهزة الموظفين وشبكة المكاتب.

## التنبيه

معدل الأخطاء غير المتوقعة لكل إصدار بعد النشر، وفشل تحميل chunks، وارتفاع contract violations
(انحراف بين نشر الواجهة والـAPI)، وتدهور p75 INP لصفحة حرجة. اربط التنبيه بإجراء: rollback الواجهة
أو feature flag.

## التشخيص من بلاغ مستخدم

1. اطلب رقم المرجع أو الوقت والشاشة. 2. ابحث بالـtraceId في traces الخادم، وبالجلسة في أخطاء الواجهة.
3. حدد الإصدارين (واجهة وAPI). 4. أعد إنتاج الحالة بنفس الصلاحيات والبيانات. 5. أصلح السبب واكتب
اختبارًا للحالة. لا تغيّر كودًا قبل دليل.

## اختبر

boundary يعرض رسالة ويبلّغ، 4xx متوقعة لا تُبلّغ، traceId يظهر للمستخدم، رفض promise غير معالج يصل للرصد،
chunk مفقود يعرض خيار التحديث.
