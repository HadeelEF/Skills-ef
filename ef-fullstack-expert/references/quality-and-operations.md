# الجودة والتشغيل

## اختر تحققًا يثبت السلوك

حدد المخاطر المتأثرة بالتغيير ثم اختر أقل مجموعة تحقق كافية. اتبع gates
المشروع. لا تكتب اختبارات لمجرد زيادة العدد أو لتكرار تفاصيل التنفيذ،
ولا تشغّل حزمة موسعة ثانية بعد حسم المخاطر دون سبب محدد.

| نوع الخطر | الدليل المناسب |
| --- | --- |
| قاعدة أعمال وحساب | اختبار حالات صحيحة وحدية وغير صحيحة |
| صلاحية على مورد | اختبار endpoint بهوية مسموحة وممنوعة ونطاق آخر |
| query/constraint/transaction | اختبار تكامل على provider ممثل للبيئة |
| نموذج علاقات ونطاق بيانات | ERD/DDL/EF متطابقة، وفشل ربط مورد من نطاق آخر أو إدخال مخالف للقيد |
| فهرس أو تحسين SQL | query/parameters وبيانات ممثلة، plan وIO/time قبل/بعد وكلفة الكتابة المتأثرة |
| تحديث متزامن أو idempotency | طلبات متداخلة تثبت invariant والنتيجة المتوقعة |
| عقد خارجي | contract/integration test أو stub موثق مع اختبار تحويل وأخطاء |
| رحلة مستخدم | اختبار متصفح للعملية وإعادة القراءة وحالات الفشل المهمة |
| مطابقة تصميم/Figma/صورة | مرجع وحالة وviewport محددة، screenshots مفحوصة وتصحيح الفروق دون إخفائها |
| Razor/MVC forms | HTTP binding وCSRF وvalidation وإعادة عرض الخيارات وPRG |
| jQuery وpartials | فتح متكرر وربط أحداث واحد وحماية النتائج من الطلبات القديمة |
| Tailwind/Bootstrap | production assets وRTL والتجاوب وتعارض resets/plugins |
| تغيير مخطط بيانات | اختبار migration على بيانات ممثلة وتوافق التطبيق |
| jobs وside effects | إيقاف worker بعد الأثر وقبل النجاح، ثم retry وتشغيل نسختين |
| Redis متعدد النسخ | إبطال من نسخة أخرى وcold cache وفشل cache دون خرق invariant |
| ملفات خاصة | upload متقطع، metadata/object غير متطابقين، وسحب صلاحية التنزيل |
| login وOIDC | callbacks وtoken validation وrevocation وتدوير المفاتيح بحسب النطاق |
| audit مطلوب | commit/rollback/retry وانقطاع sink دون فقد أو تسجيل نجاح زائف |
| React مع تبديل جلسة | نتائج متأخرة وcache وoptimistic rollback بعد تغير user/tenant |
| إعادة هيكلة ونقل ملفات | عقد المستهلك وسلوك الرحلة وDI/imports/routes، لا شكل المجلدات وحده |
| أداء | baseline وقياس ممثل ومقارنة قابلة لإعادة الإنتاج |

راجع test doubles: EF InMemory لا يثبت SQL أو isolation أو قيود
provider حقيقي. يمكن SQLite أن يفيد بعض الاختبارات، لكنه ليس بديلًا
مكافئًا لاختبار rowversion أو سلوك SQL Server. استخدم قاعدة معزولة أو
container عند توفرهما وحسب سياسة المشروع.

## تحقق من البناء والجودة العملية

شغّل أوامر المشروع الفعلية للبناء والتحليل والاختبار. افحص warnings
الجديدة والسلوك المتأثر، واحفظ رسائل الفشل ذات الصلة دون بيانات حساسة.
حافظ على الأسرار خارج المصدر؛ لا تعطل auth أو validation أو الاختبارات
لتجميل نتيجة البناء. ميز فشلًا موجودًا سابقًا عن فشل أدخله التغيير.

للواجهة افحص المتصفح والتفاعل وRTL والتجاوب والإتاحة بما يناسب المهمة.
للـAPI افحص status/body/headers والحفظ والصلاحيات. نجاح التحليل الساكن
لا يثبت اتصالًا بالخادم، ونجاح build لا يثبت سلامة رحلة المستخدم.

راجع قابلية الصيانة في الكود المسلّم: مسؤولية كل ملف وعقده، واتجاه
الاعتماديات ومصدر الحقيقة، وتسجيل الكود الجديد واستخدامه فعليًا. اختبر
عقد public component/use case وسلوك المستهلك إذا كان موضع الخطر؛ لا
تكتب اختبارات تصادق فقط على أسماء دوال أو mocks تطابق تفاصيل التنفيذ.
في React/TypeScript تحقق من وجود typecheck فعلي؛ transpile أو تنفيذ
دوال TS عبر Node لا يثبتان صحة الأنواع أو تشغيل JSX في المتصفح.

## شخّص بشكل منهجي

سجل المتوقع والفعلي وخطوات إعادة الإنتاج. تتبع request/trace ID بين
الواجهة والخادم والخدمات وقاعدة البيانات. افحص exception chain وSQL
وtimings. كوّن فرضية واختبرها بتغيير صغير. أصلح السبب ثم أعد تجربة الحالة
الأصلية وحالة مجاورة عندما يوجد خطر regression.

لا تضف cache لإخفاء استعلام سيئ قبل قياسه. لا ترفع timeouts أو pool
limits دون فهم الحمل والتسرب. وضح طريقة القياس وقيودها؛ قدّم تقدير
سعة موسومًا كافتراض مع الاختبار الذي يثبته، ولا تقدمه كنتيجة متحققة.

## جهز التشغيل بحسب بيئة المشروع

في IIS اقرأ مرجع iis-deployment-and-diagnostics من فهرس المهارة ونفذ
قالب التشغيل المناسب. الإرشادات التالية لا تكفي وحدها لتصميم نشر Windows.

حدد configuration والأسرار والـURLs والـcertificates وطريقة الدخول
والتخزين والـworkers. عند IIS تحقق من توافق OS وHosting Bundle ونمط
النشر والهوية وpermissions وreverse proxy. عند containers تحقق من
الصور المدعومة وuser والـports والـvolumes والـhealth checks.

ميز liveness عن readiness؛ لا تجعل liveness يعيد تشغيل التطبيق بسبب
انقطاع خدمة خارجية مؤقت. اضبط logs وmetrics/traces وترابطها وحدود
البيانات الحساسة، ووقت الاستجابة ومعدلات الخطأ ومؤشرات queues عند وجودها.

راجع graceful shutdown والتوقف أثناء مهمة طويلة، واستمرار session/
data-protection keys عند تعدد النسخ وفق النمط، وقابلية فحص التهيئة دون
كشف أسرار. اختر CI checks وإدارة الاعتماديات بحسب أدوات الفريق.

للنشر المصرح حدد artifact وconfig وmigration وترتيب النشر والتحقق
اللاحق وخطة rollback متوافقة مع تغييرات البيانات. حضّر التغييرات
القابلة للمراجعة قبل طلب أي إذن مطلوب، ولا تنفذ إجراء إنتاجي خارج النطاق.

## صِف مستوى الدليل بدقة

استخدم عبارات محددة: «راجعت الكود»، «نجح البناء بهذا الأمر»، «نجحت
هذه الاختبارات»، «شغّلت رحلة كذا». عند غياب SDK/DB/Browser اذكر ما
لم يُتحقق منه وأثره وخطوة التحقق التالية. لا تقدم كودًا غير مبني على
أنه اجتاز البناء، ولا نتيجة mock على أنها اختبار خدمة حقيقية.
