# ترحيل الأنظمة القديمة وتطور العقود

اقرأ عند العمل على .NET Framework أو WCF أو Web API 2 أو EF6 أو أنظمة
stored-procedure-heavy، أو عند تغيير API يستهلكه عملاء قائمون.
القاعدة: لا Rewrite شامل دون سبب قاهر؛ الترحيل التدريجي مع الإبقاء على الإنتاج يعمل.

## اجرد قبل أن تقرر

- إصدار .NET Framework، وتبعيات `System.Web` وHttpContext.Current وSession،
  وWCF bindings (basicHttp/netTcp/WS-*)، وRemoting/AppDomains، وEF6/EDMX،
  وADO.NET وstored procedures، وWindows Services، والمكتبات غير المدعومة على .NET الحديث.
- حدد ما الذي يدفع الترحيل: نهاية دعم، أمان، أداء، توظيف، استضافة. الدافع
  يحدد الأولوية؛ «تقنية قديمة» وحدها ليست سببًا كافيًا.
- تحقق من حالة أدوات الترحيل الحالية وقيودها قبل الاعتماد عليها.

## استراتيجية تدريجية (Strangler)

1. **رصد قبل التغيير**: سجلات structured وtraces ومقاييس للمسارات المهمة، كي
   تقارن السلوك قبل وبعد.
2. **Characterization tests** تثبت السلوك الحالي (بما فيه الغريب) على المسارات
   التي ستنقلها، على قاعدة SQL Server حقيقية.
3. **واجهة توجيه**: تطبيق ASP.NET Core أمام القديم يوجه المسارات المنقولة ويمرر
   الباقي (مثل YARP)، مع مشاركة المصادقة/الجلسة عبر محولات مخصصة لذلك عند الحاجة.
4. **انقل مسارًا كل مرة** خلف feature flag، مع إمكان الرجوع للمسار القديم.
   قارن النتائج (shadow/dual-run للقراءات) قبل التحويل الكامل.
5. **ملكية الكتابة**: لكل جدول كاتب واحد في أي لحظة. قاعدة مشتركة بين القديم
   والجديد مقبولة مؤقتًا بعقد واضح؛ لا dual-write بلا reconciliation.
6. **أزل القديم** بعد انتهاء الاستهلاك فعليًا (من السجلات)، لا من التوقع.

ملاحظات: المكتبات المشتركة أثناء الانتقال يمكن أن تستهدف .NET Standard 2.0 أو
multi-targeting. EF6 يعمل على .NET الحديث كخطوة وسيطة قبل EF Core. WCF يُنقل إلى
gRPC أو REST، أو CoreWCF لعملاء SOAP لا يمكن تغييرهم. stored procedures القائمة
تُستدعى من Dapper/EF دون إعادة كتابتها؛ انقل المنطق فقط عندما يوجد سبب.

## تطور API دون كسر العملاء

| آمن غالبًا (additive) | كاسر |
| --- | --- |
| endpoint جديد | حذف أو إعادة تسمية حقل أو endpoint |
| حقل اختياري جديد في الاستجابة | تغيير نوع أو صيغة (تاريخ، رقم، enum كنص/رقم) |
| معامل اختياري جديد بقيمة افتراضية محافظة | حقل مطلوب جديد في الطلب |
| قيمة enum جديدة (لعملاء متسامحين فقط) | تغيير دلالة status code أو ترتيب افتراضي أو حجم صفحة |
| | تشديد validation على مدخل كان مقبولًا |

- اجعل العملاء tolerant readers، ووثق أن قيم enum قد تُضاف.
- versioning عند التغيير الكاسر فقط: URL segment أو header أو media type وفق
  المشروع والبوابة. أعلن الإيقاف بتاريخ وheaders (Deprecation/Sunset) وراقب
  الاستهلاك قبل الإزالة.
- افحص OpenAPI diff في CI لكشف التغييرات الكاسرة، وcontract tests للمستهلكين
  المهمين.
- نسّق مع قاعدة البيانات بنمط expand/contract: أضف العمود، اكتب للاثنين أو
  backfill بدفعات، انقل القراءة، ثم أزل القديم بعد خروج الإصدار السابق.

## PATCH والتحديث الجزئي

- اختر JSON Merge Patch (RFC 7396) لتحديث بسيط، أو JSON Patch (RFC 6902) للعمليات
  على المصفوفات. فرّق صراحة بين الحقل الغائب والحقل المرسل null.
- طبق allowlist للحقول القابلة للتعديل؛ لا تطبق patch على entity مباشرة.
- اشترط `If-Match`/ETag للموارد المعرضة للتعديل المتزامن، وأعد 412 عند عدم التطابق.

## Idempotency-Key للعمليات غير idempotent

- المفتاح مرتبط بالمستخدم والعملية وبصمة الطلب، ومخزن بقيد فريد مع النتيجة.
- نفس المفتاح ونفس البصمة → النتيجة المخزنة. نفس المفتاح وبصمة مختلفة → 422.
  طلب قيد التنفيذ بنفس المفتاح → 409 أو انتظار وفق العقد. حدد مدة الاحتفاظ.

## اختبر

مستهلك بالإصدار السابق ضد API الجديدة، migration على نسخة بحجم الإنتاج، تشغيل
N وN-1 معًا على نفس القاعدة، الرجوع عن feature flag أثناء الحركة.
