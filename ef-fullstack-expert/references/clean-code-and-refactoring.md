# Clean Code وإعادة الهيكلة

## حوّل الجودة إلى قرارات يمكن مراجعتها

ميز Clean Code، أي وضوح الكود ومسؤولياته وسهولة تغييره، عن Clean
Architecture، أي اتجاه الاعتماديات وحدود السياسات والتفاصيل. التنظيم
حسب features يمكن أن يحقق كليهما؛ لا تقسهما بعدد المشاريع أو interfaces.

| الجانب | القاعدة العملية | علامة تستدعي فحصًا |
| --- | --- | --- |
| الأسماء | سمّ وفق لغة المجال والفعل والنتيجة والوحدة | Helper/Manager/Data لا تفسر مسؤولية محددة |
| الدوال | اجعل العملية بمستوى تجريد واضح ومدخلات ونتيجة مفهومين | flags تغير معناها جذريًا، nesting يخفي المسار الأساسي |
| الأنواع | عبّر عن حالات صحيحة وحدود nullable والأموال والتواريخ | any أو ! أو casts واسعة أو magic strings تخفي عقدًا |
| المسؤولية | اجمع ما يتغير للسبب نفسه وافصل السياسات عن النقل | endpoint أو component يملك كل الشبكة والقواعد والتخزين والعرض |
| الاعتماد | مرر احتياجًا صريحًا أو استخدم DI المشروع بعمر صحيح | service locator أو static mutable state أو imports دورية |
| التجريد | استخرج مفهومًا ثابتًا له مستخدم ومعنى | interface لكل class أو base class عامة لاستخدام واحد |

طبق SRP وSOLID وKISS وDRY وYAGNI كأدوات حكم. التكرار الصغير بين
سياسات قد تتغير مستقلة أقل كلفة من تجريد مشترك خاطئ. لا تستخدم مقاييس
اعتباطية مثل «كل دالة أقل من 10 أسطر» أو تقسم تعبيرًا بسيطًا إلى طبقات.

## اكتب مسارًا يمكن تتبعه

- استخدم guard clauses لتوضيح حالات الرفض مع الحفاظ على ترتيب فحص
  الصلاحيات والمدخلات وآثارها. لا تغير 404 إلى 403 أو العكس بلا قرار عقد.
- افصل الحساب الخالص عن I/O والآثار عندما يسهل الاختبار؛ لا تجعل اسم
  Get/Validate يخفي كتابة أو إرسالًا أو مسح cache. سمّ الأثر وموقعه بوضوح.
- اجعل business rule ذات مصدر خادمي واحد. يمكن للواجهة تكرار validation
  لتحسين التجربة مع عقد واضح، لكن لا تنقل الحماية من الخادم إلى React.
- لا تستخرج policy أو mapper للظهور المنظم إذا بقيت كل التفاصيل متشابكة.
  وضّح owner للحالة والمعاملة والاتصال والإلغاء وإدارة الموارد.
- ميز failure متوقعًا بعقد Result/union أو نمط المشروع، والاستثناء غير
  المتوقع بمعالجة مركزية. لا تعِد default/empty/success بعد catch يخفي الفشل.
- حافظ على stack trace، ولا تسجل exception نفسه في كل طبقة. cancellation
  ليست validation error ولا نجاح حفظ؛ صمم معناها وفق العملية والعقد.
- استخدم constants/enums/value types عندما تضبط معنى ثابتًا، دون تغيير
  serialization أو سلوك البيانات القديمة بلا migration أو توافق مقصود.
- اكتب تعليقًا لسبب غير ظاهر أو قيد أو invariant؛ احذف الكود الميت
  والتعليقات المضللة ضمن النطاق، دون إزالة API أو إعداد مستخدم لعدم رؤيته محليًا.

## حسّن الكود القائم تدريجيًا

1. اقرأ المسار والمستهلكين واختباراتهم؛ حدد السلوك العام الذي يجب حفظه:
   routes وDTOs وstatus/errors والصلاحيات وترتيب الآثار وtransaction boundaries.
2. شغّل baseline المتاح. عند منطق مهم بلا تغطية، أضف characterization
   tests لسلوك مشروع مقبول؛ لا تثبت bug معروفًا باعتباره المتطلب الصحيح.
3. اختر أصغر seam مفيد: استخرج policy خالصة أو API adapter أو component
   بعقد واضح، وانقل ملفًا مع تعديل imports/DI/exports/اختباراته الفعلية.
4. افصل تعديل السلوك المطلوب عن إعادة التسمية والتنسيق في تغييرات مفهومة؛
   لا توسع المهمة إلى إعادة كتابة شاملة أو ترقية اعتماديات غير مرتبطة.
5. أعد فحص السلوك والمخاطر المتأثرة، ثم راجع diff واحذف المسار القديم
   إذا استُبدل بالفعل. لا تترك تنفيذين متنافسين أو compatibility shim أبديًا.

انتبه لما يخفيه استخراج الدوال: تكرار query، نقل enumeration خارج عمر
DbContext، فقد cancellation، تغيير rounding/culture، transaction أضيق،
أو إعادة تركيب نموذج React وفقد مسودته بسبب identity/key مختلفة.

## استخدم الأدوات كحواجز جودة متناسبة

اتبع .editorconfig وnullable/analyzers في .NET، وTypeScript strict
وESLint/Rules of Hooks وformatter في الواجهة وفق المشروع. لا تضف حزمتين
تفرضان تنسيقًا متعارضًا. لا تستخدم تعطيل التحذيرات أو @ts-ignore أو
خفض الصرامة لتمرير تغيير. أي suppression استثنائي ضيق ومبرر وقابل للمراجعة.

في مشروع جديد ضع أوامر build/typecheck/lint/test واضحة ومتوافقة مع
الإصدارات. في القائم عالج تحذيرات التغيير وميزها عن baseline؛ لا تفرض
warnings-as-errors على مستودع قديم ضمن تعديل صغير بلا خطة انتقال.

## راجع قبل التسليم

تتبع حالة نجاح وحالة فشل مؤثرة: هل العقد مفهوم، والصلاحية محفوظة،
والحفظ حقيقي، ورسالة الواجهة صادقة؟ هل يمكن تعديل قاعدة واحدة في مكان
معروف؟ هل الاعتماديات أحادية الاتجاه والكود الجديد مستخدم فعلًا؟
افحص السلوك أولًا ثم الأمان والعقد والبيانات ثم القابلية للصيانة والأداء.
ميّز bug مثبتًا عن اقتراح أسلوبي؛ وثّق الأثر وموضعه والإصلاح، لا الانطباع.
اختبارات سلوك قليلة مفيدة أفضل من اختبارات أسماء الملفات وعدّ الأسطر
أو mocks تؤكد ترتيب تفاصيل لا يهم المستهلك. لا تدّعِ جودة مثالية أو خلوًا
من الأخطاء لمجرد lint ناجح؛ سلّم أدلة النطاق الفعلي.
