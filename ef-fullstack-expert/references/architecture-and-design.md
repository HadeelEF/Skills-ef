# المعمارية والتصميم

## افصل مستويات القرار

| المستوى | السؤال |
| --- | --- |
| حدود الحل | من يستخدمه؟ ما الأنظمة الخارجية ومصادر البيانات والثقة؟ |
| التشغيل والنشر | تطبيق واحد أم خدمات مستقلة؟ ما متطلبات العزل والتوسع؟ |
| الوحدات | ما القدرات التجارية؟ من يملك كل نموذج وبيانات وعقد؟ |
| حالات الاستخدام | كيف ينفذ الطلب ومن يفرض قواعده ومعاملته وصلاحيته؟ |
| اتجاه الاعتماديات | كيف يُعزل منطق الأعمال عن تفاصيل البنية التحتية؟ |
| تنظيم الكود | ميزات أو وحدات أو طبقات؛ ما الذي يتغير معًا؟ |

Modular Monolith يحدد حدودًا منطقية داخل نشر موحد. Vertical Slices
ينظم السلوك بحسب حالات الاستخدام. Feature-based تنظيم للملفات والميزات.
Clean Architecture يركز على اتجاه الاعتماديات. بيّن كيف تتكامل هذه
الخيارات دون اعتبار أسماء المجلدات دليلًا على تحققها.

## اتخذ القرار من خصائص المشكلة

لاختيار نمط كود أو توزيع اقرأ patterns-and-architecture-playbook من
الفهرس؛ اربط النمط بخطر أو تغير فعلي ومثال تنفيذ واختبار، لا باسمه فقط.

- ابدأ بأبسط تصميم يحقق القيود. لتطبيق صغير قد يكفي تنظيم حسب الميزات؛
  للوحدات التجارية المتعددة قيّم Modular Monolith بحدود واضحة.
- اختر خدمات مستقلة لحاجة لعزل نشر أو توسع أو ملكية فرق أو حدود أمنية
  مختلفة؛ قيّم الاتساق والتشخيص والشبكة والتشغيل المصاحب.
- استخدم DDD للأجزاء ذات القواعد المعقدة؛ يمكن أن تبقى أجزاء CRUD
  بسيطة. عرف المصطلحات والكيانات والقيم وinvariants قبل تكثير الطبقات.
- افصل القراءة والكتابة منطقيًا عندما يفيد ذلك؛ لا يستلزم CQRS قاعدة
  ثانية أو event sourcing أو broker أو مكتبة mediator.
- استخدم events داخل العملية عندما تلائم المعاملة. للتكامل الخارجي
  حدد العقد ونسخته والتسليم وإعادة المحاولة والترتيب إن كان مهمًا.
- قِس حاجة caching، وعرّف الملكية وTTL والإبطال والعزل قبل إضافته.

## صمم حدودًا يمكن فرضها

عرّف لكل module مسؤولية وبيانات يملكها وعمليات عامة محدودة. امنع الكتابة
المباشرة في بيانات module آخر عبر سياق مشترك غير مقيد؛ استخدم عقدًا
معلنًا أو تنسيق use case واضحًا حسب تصميم المشروع.

افصل قواعد الأعمال عن HTTP والتخزين عندما يعزز وضوحها واختبارها.
استخدم DTOs عند حدود API. لا تنشئ Generic Repository أو Unit of Work
فوق ORM تلقائيًا؛ اطلب قيمة محددة من كل تجريد.

اجعل مشاركة الكود مقصودة: primitives ثابتة أو عقد مشترك حقيقي. تجنب
مشروع Shared يستوعب التفاصيل ويعيد ربط الوحدات. اختبر الحدود المؤثرة
عند تعدد الوحدات أو ازدياد خطر التداخل.

## صمم لظروف التشغيل

ارسم topology الويب بحسب الحاجة: client وedge/reverse proxy ثم web/BFF/API،
وعمال وDB وcache وfile store وIdP والتكاملات. حدد process boundaries
وtrust boundaries ومالك كل state. API Gateway لا يستبدل resource authorization
داخل التطبيق؛ BFF مفيد عند حاجة session/token handling أو عقود واجهة مستقلة.
اضبط مسار HTTPS/forwarded headers، ونشر static assets مقابل SSR runtime،
وحماية الملفات الخاصة ومفاتيح الجلسات عبر النسخ. لا تضف كل مكون افتراضيًا.

حدد أهداف الأداء والتوافر والحجم والتعافي بما يسمح باختبارها. ميز
أهداف المنتج عن التقدير، ولا تخترع SLA؛ قدّم تقدير سعة موسومًا كافتراض
(قالب تقدير السعة) بدل الامتناع، ولا تصفه بأنه مثبت. راجع فشل
الهوية الخارجية، وبطء البيانات، وتكرار الرسائل، وإعادة تشغيل العمال،
وتعارض التعديل، وانتهاء المهلة وإعادة محاولة العميل.

اربط الاستضافة بالتقنيات: SPA ثابتة تختلف عن SSR يتطلب runtime؛
وIIS أو containers أو cloud تخضع للبنية الفعلية. لا تفترض أن .NET
يفرض Azure أو أن React يفرض Next.js.

راجع transactional boundaries وidempotency وoutbox عند الآثار الخارجية،
والـtimeouts وretry budgets والتدهور عند فشل cache/IdP/storage. عرّف
RTO/RPO ومتطلبات backup/restore مع المالك عندما تكون جزءًا من النطاق؛
لا تعتبر health endpoint دليلًا على قدرة التعافي أو صحة كل business flow.

## ترجم Software Architecture إلى كود .NET

حدد مسار use case: transport adapter → application orchestration → قواعد
ونموذج أعمال → ports للبنية الخارجية حيث تفيد. composition root يربط DI؛
اجعل الاعتماديات نحو السياسات المستقرة، دون reference عكسي من domain إلى
ASP.NET أو storage provider. لا تشترط مشروعًا لكل طبقة في تطبيق صغير.

للـdomain المعقد حدد bounded contexts وaggregates وinvariants وvalue
objects وحدود transaction؛ لا تجعل aggregate يحمّل كل علاقات المؤسسة.
في CRUD بسيط قد يكون handler واضح مع EF كافيًا. لا تعتبر كل entity
aggregate أو كل تغيير event sourcing، ولا توزع قواعد واحدة بين controller
وmapper وReact. ضع business policy في موقع واضح قابل للاستدعاء والاختبار.

قيّم الأنماط لغرض محدد: strategy لاختلاف سياسة فعلية، adapter لتكامل،
pipeline لسلوك مشترك، state machine لانتقالات عملية؛ تجنب abstractions
للاستخدام المحتمل فقط. ناقش تكلفة التغيير والترخيص والتشغيل والفريق.
اربط كل قرار مؤثر بملفات ومشاريع وعقود ومخطط بيانات وفشل ممثل؛ تحقق من
cycles وحدود module والتبعيات باختبار معماري عند وجود خطر فعلي لتآكلها.

## سلّم التصميم بقدر الحاجة

للقرار الكبير قدم سياقًا وقيودًا واختيارًا وبديلًا وتبعات وخطة تطور.
استخدم مخططًا فقط عندما يوضح علاقة صعبة. اربط المكونات بمجلدات ومشاريع
وعقود حقيقية عند وجود كود. دوّن ADR قصيرًا للقرارات التي يصعب عكسها،
وحدّث الوثيقة الموجودة بدل إنشاء وثائق متكررة للتغييرات الصغيرة.
