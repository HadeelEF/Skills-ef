# معمارية التفويض

اقرأ عند تصميم صلاحيات نظام، أو إضافة دور أو صلاحية، أو مراجعة IDOR، أو
صلاحيات على مستوى الصف. مثال مطبق كامل: `assets/examples/golden-use-case`.
القاعدة: الواجهة تُخفي، والخادم يقرر، وقاعدة البيانات تحمي الحد الأخير.

## اختر النموذج من شكل القاعدة

| النموذج | يناسب | حدوده |
| --- | --- | --- |
| RBAC (أدوار) | صلاحيات خشنة مستقرة: مدير نظام، مدقق | انفجار الأدوار عند كل استثناء؛ لا يعرف المورد |
| Permission-based | عمليات دقيقة (`requests.approve`) تُجمع في أدوار قابلة للإدارة | لا يعرف النطاق وحده |
| Policy-based (ASP.NET Core) | تركيب شروط: صلاحية + claim + MFA حديث | سياسة بلا مورد لا تمنع IDOR |
| Resource-based | القرار يعتمد على المورد: مالك، إدارة، حالة | يتطلب تحميل المورد أولًا وفحصًا في كل مسار |
| ABAC / scope | سمات المستخدم والمورد والسياق (إدارة، تصنيف، وقت) | تعقيد الاختبار والتدقيق؛ ابدأ بأقل السمات |

النمط العملي لأنظمة الصندوق: **صلاحيات مجمعة في أدوار + نطاق (إدارة/جهة/مساحة عمل)
+ فحص resource-based في كل use case**.

## نموذج البيانات

`Permissions(Code)`، `Roles`، `RolePermissions`، `UserRoleAssignments(UserId, RoleId,
ScopeType, ScopeId, ValidFrom, ValidTo, GrantedBy)`. الإسناد مرتبط بنطاق ومدة ومانح؛
كل منح وسحب يُدقق. لا تخزن الصلاحيات في الواجهة أو في local storage.

## التطبيق في ASP.NET Core

- `SetFallbackPolicy` تتطلب مستخدمًا مصادقًا: endpoint نُسي تأمينه لا يصبح عامًا.
- policies للصلاحيات الخشنة على endpoints؛ `IAuthorizationService.AuthorizeAsync(user,
  resource, requirement)` داخل use case بعد تحميل المورد.
- عدد كبير من الصلاحيات: `IAuthorizationPolicyProvider` مخصص يبني policy من اسمها
  (`perm:requests.approve`) بدل تسجيل مئات policies يدويًا.
- القوائم والبحث والتصدير والعدّ: طبّق النطاق في الاستعلام نفسه (`WHERE DepartmentId IN
  (@scopes)`) لا بفلترة النتائج في الذاكرة، ولا بفحص كل عنصر بعد جلب الكل.
- المرفقات والملفات: فحص المورد الأب في كل تنزيل وعند إصدار رابط مؤقت.
- jobs: أعد الفحص عند التنفيذ بهوية المبادر ونطاقه المخزن، لا بهوية الخدمة الواسعة.

## التوقيت والإبطال

- claims في token تبقى حتى انتهائه. الصلاحيات المتغيرة أو الحساسة تُقرأ من مخزن التطبيق
  (مع cache قصير وإبطال عند التغيير) لا من token طويل العمر.
- تعطيل مستخدم أو سحب دور فوري المطلوب: security stamp/version يُفحص في كل طلب، أو
  جلسات خادمية، لا انتظار انتهاء token.
- العمليات الحرجة (تغيير صلاحيات، اعتماد مالي كبير): re-authentication أو MFA حديث كشرط policy.

## الحماية في قاعدة البيانات

للبيانات الحساسة أضف SQL Server RLS كخط دفاع، أو على الأقل FK مركبة تتضمن النطاق لمنع
ربط سجل بنطاق آخر. حساب التطبيق بلا صلاحيات DDL؛ حسابات تقارير للقراءة فقط.

## 403 أم 404

خارج النطاق: 404 إذا كان مجرد معرفة وجود المورد معلومة حساسة، و403 إذا كان الوجود
معروفًا والرفض يحتاج تفسيرًا للمستخدم. وحّد السياسة في المشروع واختبرها.

## اختبر

لكل endpoint حساس: مسموح، ممنوع، نطاق آخر، مستخدم معطل، صلاحية مسحوبة خلال الجلسة،
عبر المسار المباشر والبحث والتصدير والمرفقات والـjob. التفويض غير المختبر غير موجود.
