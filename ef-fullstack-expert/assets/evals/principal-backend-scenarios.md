# سيناريوهات تقييم سلوك المهارة (Principal Backend)

استخدم هذه السيناريوهات لاختبار المهارة فعليًا بعد أي تعديل: أعط النموذج
السيناريو مع المهارة، وقارن الإجابة بالسلوك المتوقع. النص الجيد للمهارة لا
يثبت السلوك؛ هذه الاختبارات تثبته. سجل النتيجة والتاريخ والنموذج.

## 1. حادث: بطء بعد النشر
**المدخل:** «Production API أصبحت بطيئة بعد deployment. CPU التطبيق والذاكرة
طبيعيان، SQL CPU مرتفع، الطلبات تتكدس.»
**المتوقع:** يؤكد الأثر ويربطه بالنشر؛ يقترح rollback أو فرض الخطة الجيدة كتخفيف؛
يفتح Query Store للاستعلامات المتراجعة في نافذة النشر؛ يفحص implicit conversion
وفهرسًا مفقودًا وparameter sniffing وشكل استعلام EF جديد؛ لا يقترح رفع timeouts
أو إضافة cache أولًا.
**رسوب:** تغيير كود قبل جمع دليل، أو «أضف Redis».

## 2. تزامن المخزون
**المدخل:** مستخدمان يحجزان من نفس الكمية في الوقت نفسه بكود يقرأ ثم يفحص ثم يحفظ.
**المتوقع:** يحدد السباق؛ يقترح conditional UPDATE مع فحص affected rows أو rowversion،
ويعيد 409؛ يكتب اختبار تكامل بطلبين متزامنين على SQL Server حقيقي.
**رسوب:** `lock` في C# كحل، أو اختبار بـEF InMemory.

## 3. خمس نسخ
**المدخل:** «سنشغل التطبيق على 5 خوادم خلف load balancer. ماذا ينكسر؟»
**المتوقع:** IMemoryCache، BackgroundService ×5، الملفات المحلية، locks، Data
Protection keys، SignalR backplane، rate limiter داخل الذاكرة، migrations عند startup،
outbox dispatcher بلا حجز، السجلات المحلية.

## 4. Microservices
**المدخل:** «نريد بناء نظام إدارة الطلبات الداخلي بـMicroservices لأنه أحدث.» (فريق 4 مطورين)
**المتوقع:** يوصي بـModular Monolith مع حدود واضحة، يشرح كلفة التوزيع والتشغيل،
ويذكر الشروط التي تبرر الانتقال لاحقًا، في صيغة ADR.

## 5. مراجعة كود
**المدخل:** controller يستخدم `.Result`، و`Update(dto)` مباشرة على entity، وتنزيل
مرفق بالمعرف دون فحص النطاق، و`catch (Exception) { return null; }`، وstring SQL مدمج.
**المتوقع:** ترتيب Critical (IDOR، SQL injection، mass assignment) ثم High
(sync-over-async) ثم Medium؛ لكل نتيجة شرط الظهور والأثر والإصلاح والاختبار.

## 6. تقدير سعة
**المدخل:** «النظام سيخدم 10,000 مستخدم متزامن. كم نحتاج؟»
**المتوقع:** تقدير موسوم (RPS من الفاصل الزمني، Little's Law للاتصالات)، نقطة
التشبع المتوقعة، واختبار حمل يثبت. **رسوب:** رفض التقدير كليًا، أو أرقام بلا افتراضات.

## 7. نشر رسالة بعد الحفظ
**المدخل:** «بعد اعتماد الطلب نحفظ في DB ثم نرسل SMS ونشعر نظام ERP.»
**المتوقع:** يرصد dual write؛ outbox في نفس المعاملة، dispatcher مع lease، مستهلك
idempotent، idempotency مع مزود SMS، DLQ وreconciliation، ولا وعد بـexactly-once.

## 8. تغيير عمود على 500 مليون صف
**المتوقع:** expand/contract، عمود جديد، backfill بدفعات مع مراقبة log/locks،
توافق N/N-1، فحص دعم ONLINE في edition، خطة رجوع؛ لا migration مباشرة.

## 9. ملف 2GB
**المتوقع:** streaming بـMultipartReader، حدود في IIS وKestrel وForm، checksum
أثناء التدفق، حالة pending وفحص، تنزيل بـRange بعد تفويض؛ لا IFormFile/ReadAllBytes.

## 10. Legacy
**المدخل:** «نظام Web API 2 وWCF على .NET Framework 4.6 يعمل يوميًا. نريد تحديثه.»
**المتوقع:** جرد، رصد وcharacterization tests، strangler عبر proxy، نقل مسار بمسار
خلف flags، ملكية الكتابة؛ لا rewrite شامل.

## معيار الدرجة

- 10/10 للسيناريو: كل عناصر «المتوقع» حاضرة، لا عنصر «رسوب»، والقرار قابل للتنفيذ.
- المهارة بمستوى Principal عندما تحقق 9 من 10 سيناريوهات على الأقل بشكل متكرر؛ ولمستوى Elite طبّق ورقة التقييم في آخر الملف على الـ20 سيناريو.

## سيناريوهات إضافية

### 11. Cache stampede
**المدخل:** «بعد انتهاء TTL لمفتاح لوحة القيادة يرتفع SQL CPU إلى 100% لدقيقة.»
**المتوقع:** يشخص stampede؛ single-flight لكل مفتاح داخل النسخة، TTL مع jitter، تحديث
مسبق أو stale-while-revalidate، حد لحمل DB؛ ينبه أن قفل النسخة لا يمنع التزامن بين النسخ.

### 12. تصميم JWT
**المدخل:** «نريد JWT صلاحيته 30 يومًا ونخزنه في localStorage للتطبيق React.»
**المتوقع:** يرفض الصيغة مع البديل: BFF بـcookie HttpOnly أو code+PKCE مع access قصير،
refresh rotation مع reuse detection، إبطال فوري عبر security stamp، التحقق من issuer/audience.

### 13. SignalR مع نسخ متعددة
**المتوقع:** backplane أو خدمة مدارة، sticky sessions أو WebSockets فقط، groups تُعاد عند
الاتصال، الحقيقة من API بعد reconnect، token في query لا يُسجل.

### 14. تسريب بين مستأجرين
**المدخل:** «تقرير التصدير أظهر بيانات جهة أخرى.»
**المتوقع:** يعامله Critical: احتواء فوري (تعطيل التصدير)، تحديد النطاق من audit، فحص
`IgnoreQueryFilters`/raw SQL/مسار الـjob، إصلاح بفلترة في الاستعلام + FK مركبة + اختبار
cross-tenant، وتقييم الإبلاغ وفق سياسة المؤسسة.

### 15. تسرب ذاكرة
**المتوقع:** dumps متباعدة ومقارنة `dumpheap -stat` و`gcroot`، يميز managed عن native،
يبحث عن cache بلا حد وevent handlers وstatic collections، ولا يعتبر recycle المجدول إصلاحًا.

### 16. استنزاف connection pool
**المتوقع:** يفحص المعاملات الطويلة والاتصالات غير المغلقة والتوازي غير المحدود والـHTTP
داخل المعاملة؛ لا يرفع Max Pool Size كحل.

### 17. Job يتكرر
**المدخل:** «إشعار الرواتب أُرسل مرتين بعد نشر على خادمين.»
**المتوقع:** جدولة على النسختين أو lease منتهٍ؛ scheduler clustered أو قفل في DB مع
fencing، ومفتاح idempotency لكل (الدورة، المستلم)، ومراجعة سجل التسليم.

### 18. تغيير كاسر في API
**المدخل:** «نريد تحويل الحقل amount من رقم إلى كائن {value, currency}.»
**المتوقع:** إضافة حقل جديد بجانب القديم، deprecation بتاريخ ومراقبة الاستهلاك، أو
version جديد؛ OpenAPI diff في CI؛ لا كسر للعملاء الحاليين.

### 19. DR
**المدخل:** «ما خطة استعادة النظام إذا تلف الخادم بالكامل؟»
**المتوقع:** RPO/RTO من المالك، backups full/diff/log، استعادة مجربة ومقاسة، مفاتيح Data
Protection والشهادات والأسرار والملفات وتهيئة IIS، runbook وتدريب دوري.

### 20. 500.30 بعد النشر
**المتوقع:** Event Viewer وstdout مؤقت، ثم config/أسرار/هوية App Pool/runtime؛ rollback
للـartifact السابق إن طال؛ لا تفعيل Development في الإنتاج.
