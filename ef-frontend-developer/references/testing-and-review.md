# التحقق من الوظائف والمظهر

## Choose checks from the actual change

استمد الفحص من معايير القبول والمخاطر التي أدخلها التغيير. إصلاح نص لا
يحتاج اختبارات وحدات جديدة؛ بحث غير متزامن أو إرسال نموذج يحتاج فحصًا
للسلوك الذي قد يفشل. لا تكتب اختبارًا يكرر التنفيذ أو يثبت وجود عنوان فقط.

ابدأ بأوامر المشروع المتاحة ذات الصلة: type check وlint والاختبارات والبناء.
اقرأ تعريف الأمر ونتيجته؛ عدم وجود script ليس نجاحًا، ونجاح خادم التطوير
ليس نجاح بناء الإنتاج. لا تعطل قاعدة أو اختبارًا لإخفاء خلل أحدثه التنفيذ.

استخدم Vitest/React Testing Library أو أدوات المشروع للمنطق والسلوك الذي
يستفيد من اختبار قابل للتكرار، وPlaywright أو أداة المتصفح المتاحة للرحلة
الحقيقية. فضّل الوصول عبر role وname وlabel؛ احتفظ بالمعرفات الاختبارية
لما لا يمكن تمييزه بثبات عبر الدلالة. لا تربط كل اختبار بتفاصيل DOM الداخلية.

لـReact، اقرأ [التشخيص والاختبارات السلوكية](debugging-and-evolution.md)
عند إصلاح race أو فقد الحالة أو معمارية تزامن. تغطية نسبة أسطر مرتفعة لا
تثبت سلامة هذه المسارات؛ اختبر النتيجة التي يحافظ عليها المستخدم.

## Verify the running page

بعد تشغيل الخادم، افتح الصفحة فعليًا قبل اعتبار بيئة المعاينة جاهزة.
تحقق من أن المحتوى المعني ظهر، وأنه ليس صفحة فارغة أو overlay خطأ، وأن
الأصول والمسار المطلوب يعملان. اتبع مهارة أداة المتصفح المتاحة قبل استخدامها.

التقط أخطاء JavaScript وconsole وأخطاء الطلبات منذ تحميل الصفحة عندما
تدعم الأداة ذلك. قراءة مصفوفة لم تُربط أصلًا بالـconsole لا تثبت غياب الأخطاء.
افحص 4xx/5xx المؤثرة أيضًا؛ بعض الأدوات تعد الاستجابة الفاشلة طلبًا مكتملًا.
ميّز الأخطاء المحقونة عمدًا في سيناريو فشل عن أخطاء غير متوقعة.

اختبر ما يهم المستخدم في المسار المنفذ، مثل:

| السلوك | دليل مفيد |
| --- | --- |
| دخول مسار أو العودة إليه | فتح مباشر وتحديث ورجوع صحيح مع الحالة المطلوبة |
| البحث/المرشحات | تغير بيانات متوقع، حفظ المعايير، وعدم تغلب استجابة قديمة |
| النموذج | منع غير الصالح، إرسال صالح، انشغال، نتيجة صحيحة، بقاء المدخلات عند الفشل |
| تبديل اللغة | نصوص واتجاه صحيحان مع حفظ السياق المطلوب |
| لوحة المفاتيح | الوصول للأفعال، ترتيب مفهوم، focus مرئي والعودة من الحوار |
| إعادة المحاولة | نفس العملية المقصودة دون تكرار كتابة غير مضمون |

لا تنفذ أفعالًا حقيقية ذات أثر خارجي لمجرد اختبارها؛ استخدم fixtures أو
بيئة الاختبار المتاحة ضمن الصلاحيات. بيّن في التقرير إن كان API حقيقيًا
أو mock، حتى لا تتحول نتيجة محلية إلى ادعاء تكامل منشور.

## Inspect the visual output

شاهد لقطات فعلية أو مخرجات المتصفح؛ حفظ screenshot دون فتحها ليس مراجعة
بصرية. قارن بالتصميم أو المواصفات عند نفس الحالة والمقاس واللغة متى أمكن.
افحص بالقدر المتعلق بالتغيير:

- مقاس desktop ومقاس ضيق ممثلان، بالعربية والإنجليزية عند شمول التغيير لهما.
- التكوين والخط الفعلي والوزن والتفاف النص والشعار والمسافات والتباين.
- overflow والقص والعناصر الثابتة وتداخلها مع النص أو focus.
- انشغال وفراغ وخطأ ومحتوى طويل إذا كانت ممكنة وتؤثر في التخطيط.
- القوائم والحوارات وحالات الأزرار والمدخلات المتأثرة.

المقاسات المختارة أمثلة اختبار وليست breakpoints إلزامية. استخدم أدلة
متصفح إضافية لتحميل الخطوط والأصول واتجاه المستند، وافتح اللقطات للتحقق
من أثرها المرئي. لا يحل screenshot جميل محل اختبار الأفعال.

إن استخدمت مقارنة صور آلية، ثبّت البيانات والوقت والخطوط والحركة المناسبة
للاختبار. حلل الفرق قبل تحديث baseline؛ لا تعتمد صورة جديدة لإسكات فشل.

## Accessibility and performance evidence

اجمع الفحص الآلي مع فحص لوحة المفاتيح والتركيز والمحتوى المتعلق بالمهمة.
أداة axe أو Lighthouse تكشف بعض المشكلات ولا تمنح شهادة امتثال شاملة.
قياسات الأداء تحتاج بيئة وحالة تحميل معلومتيْن؛ لا تستخدم رقم بيئة التطوير
كدليل على سرعة الخدمة المنشورة.

مراجع: [Playwright accessibility testing](https://playwright.dev/docs/accessibility-testing)،
[Vitest](https://vitest.dev/guide/)،
[React Testing Library](https://testing-library.com/docs/react-testing-library/intro/).

## Correct, then report accurately

أصلح الفشل المرتبط بالطلب وأعد فحص المسار المتأثر. وسّع الاختبار عندما
يبقى خطر محدد أو يفرض المشروع بوابة لازمة، ثم توقف عند تحقق النتيجة؛
لا تنشئ جولات فحص لا تغير الحكم على العمل.

في التسليم، ميّز بين **نجح فعلًا**، **فشل ويحتاج معالجة**، و**لم يُفحص**.
اذكر الأمر أو السلوك والبيئة عند الحاجة، دون إغراق المستخدم بسجلات خام.
إذا تعذر تشغيل المتصفح أو الخادم، احتفظ بالكود وأدلة الفحوص الممكنة واذكر
حد النتيجة. لا تصف الواجهة بأنها مطابقة بصريًا أو جاهزة للإنتاج دون دليل
مناسب لهذا الادعاء. احفظ أدلة المشروع خارجه عن مجلد هذه المهارة.
