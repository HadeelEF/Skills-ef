# معمارية React وحدود المكونات

## Propose an implementable architecture

ابدأ من المستخدمين والمهام وحساسية البيانات وحجم الفريق والاستضافة
والتكاملات والتغييرات المتوقعة. اربط الاقتراح بالمشروع الحالي؛ لا تجعل
اسم نمط معماري أو عدد الشاشات سببًا كافيًا لتبنيه.

عند طلب معمارية، قدم ما يلزم من: الاختيار وسببه، حدود الميزات واتجاه
الاعتماد، مكان البيانات والحالة، نموذج العرض والمسارات، المكتبات اللازمة،
مسار تنفيذ ممثل، وطريقة فحصه. وضّح تكلفة البديل الجدي وشرط الانتقال إليه.
للعمل المركب يكفي قرار مختصر في وثائق المشروع؛ لا تفرض ADR لكل مكوّن.

| وضع المشروع | اتجاه يدرس بحسب الحاجة |
| --- | --- |
| صفحة أو ميزة محدودة | تجميع قريب من الاستخدام ومكونات واضحة دون طبقات غير مستخدمة |
| منتج بعدة مجالات أعمال | تنظيم حول features وحدود تصدير معلومة ونظام UI مشترك لما يتكرر فعلًا |
| أكثر من تطبيق يتشارك أصولًا أو عقودًا | packages مشتركة عندما تتضح دورة الإصدار والاستخدام؛ monorepo قرار عمل وبناء |
| فرق تحتاج نشرًا مستقلًا فعليًا | قيّم microfrontends مع تكلفة التوجيه والهوية والإصدارات والتشغيل |
| مشروع قائم | طوّر جزءًا محددًا داخل حدوده ثم عمّم النمط بعد ثبوت فائدته |

## Dependency direction

مثال قابل للتكييف: `app` تجمع المسارات وproviders؛ ميزة `requests` تملك
نموذجها وتدفقها وواجهتها؛ `ui` توفر primitives عامة؛ adapters تتعامل مع
النقل والتخزين. ليست أسماء مجلدات إلزامية، ولا يلزم إنشاء كل طبقة إذا
لم تعزل مسؤولية حقيقية.

- اجعل اتجاه الاستيراد مفهومًا، وتجنب اعتماد المكوّن العام على ميزة أو
  استيراد ميزتين لتفاصيل بعضهما بما يصنع دورة.
- صدّر العقد الذي يحتاجه المستهلك، وأبقِ التفاصيل داخل حد الميزة. افحص
  barrel exports إذا سببت دورات أو عبور وحدات خادم إلى العميل.
- افصل قواعد المجال المهمة عن JSX والنقل بما يسمح بفحصها وتغيير API؛
  لا تنشئ طبقات DTO/repository/use-case متطابقة لمجرد شكل معماري.
- adapter يفيد لاستبدال fixture بتكامل أو عزل متصفح/مزود. لا يلزم
  dependency injection framework كي يصبح الفصل قابلًا للاختبار.

## Component boundaries

اقسم بحسب المسؤولية المتكررة وحدود السلوك، لا بحسب كل عنصر HTML. حافظ على
اتجاه واضح بين مصدر البيانات، تحويلها إلى نموذج العرض، والمكونات التي تعرضها.
الشكل المتكرر قد يستحق مكوّنًا؛ تشابه العرض وحده لا يبرر ربط رحلتين مختلفتين
بمكوّن عام مليء بخيارات خاصة.

ضع قيم التصميم المشتركة في نظام المشروع، وواجهات المكونات في حدود مفهومة.
لا تجعل كل شاشة تنسخ الألوان والمقاسات أو تحل الاتجاه وحدها. استخدم HTML
الدلالي كأساس؛ الزر فعل والرابط انتقال، واسم المكوّن لا يمنحه إتاحة تلقائية.

في TypeScript، عرّف أنواع المجال وخصائص المكونات التي تمنع حالات غير صحيحة.
استخدم اتحادات واضحة للحالات عندما تفيد، بدل تجميع flags تسمح بظهور النجاح
والفشل والانشغال في الوقت نفسه. لا تستخدم `any` أو تحويلًا قسريًا لإخفاء
عقد غير مفهوم. نوع TypeScript لا يتحقق من بيانات الشبكة أثناء التشغيل.
تفاصيل تصميم العقود في [TypeScript](typescript-contracts.md).

حدد controlled/uncontrolled للمكوّن: مالك القيمة وعلاقة `value` و`onChange`
و`defaultValue`. لا تنسخ props إلى state وتزامنها دائمًا؛ عرّف متى يبدأ
تعديل جديد ومتى يُعاد ضبطه. تغيير اللغة لا يعيد تركيب نموذج بلا قصد.

استخدم children/slots أو تركيب مكونات صغيرة عندما يوضح المسؤولية.
Compound components وpolymorphic APIs تعالج حاجة مثبتة، مع حفظ الدلالة
وrefs والإتاحة. فرّق بين primitive عامة ونمط منتج متكرر وشاشة تربط البيانات.
في مكتبة UI مشتركة عرّف variants والحالات وRTL وعقد التوافق؛ استخدم
Storybook عندما تحتاج تطويرها ومراجعتها مستقلة.

## Put state in its proper place

| نوع الحالة | مكان مناسب |
| --- | --- |
| فتح قائمة أو قيمة لم تُرسل بعد | حالة محلية للمكوّن أو النموذج |
| البحث والفرز والصفحة القابلة للمشاركة والعودة | URL إذا نصت التجربة على ذلك، مع تحقق من القيم |
| بيانات الخادم وحالة جلبها | آلية الإطار أو مكتبة الاستعلام، مع نطاق التخزين وإبطال المناسب |
| اللغة أو تفضيل عام لازم | طبقة الترجمة/السياق المتاحة؛ سجل أولوية المصدر |
| قيمة محسوبة من بيانات موجودة | اشتقها أثناء العرض؛ لا تنسخها إلى حالة متزامنة بلا حاجة |

تجنب تخزين نفس الحقيقة في URL وstate وstore بدون مصدر مرجعي واحد وآلية
مزامنة واضحة. تعامل مع رجوع المتصفح والتحديث والروابط العميقة، ولا تجعل
قراءة URL في render تغيّر الحالة بلا ضابط.

استخدم Effects لمزامنة نظام خارجي عند الحاجة؛ لا تضف Effect لكل عملية حساب
أو فعل يمكن تنفيذه في معالج الحدث. عالج التنظيف وإلغاء الاشتراكات والطلبات.
لا تخف مشاكل دورة الحياة بتعطيل Strict Mode. راجع
[React: You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect).

## Ownership across boundaries

Context وسيلة تمرير مشتركة؛ حدد نطاق provider وما يسبب تغير قيمته.
Store خارجي يتطلب قرار الاشتراكات وselectors وحياة الحالة. في SSR لا
تشارك store يحمل بيانات مستخدم بين الطلبات. اختر المكتبة من
[مرجع الاختيار](library-selection.md) بعد تحديد طبيعة الحالة.

عند تعديل نسخة محلية من بيانات الخادم، حدد قاعدة المصالحة: ماذا يحدث عند
refetch أو حفظ متزامن أو الانتقال لسجل آخر؟ استخدم version/conflict من
العقد إن توفر. لا تختلق ضمانًا لمنع تعارض لا يستطيع الخادم كشفه.

حدود Server Components وNext.js والتخزين المؤقت وVite والمسارات في
[العرض والتوجيه](rendering-and-routing.md). حدود Hooks والهوية والمزامنة
والتزامن في [هندسة React](react-engineering.md).

## Keep extensions proportional

أدخل مدير حالة عامًا إذا احتاجت حالة عميل مشتركة فعلًا إليه، لا بدل فهم
مصدرها. استخرج hooks عندما تعزل سلوكًا واضحًا. أضف memoization أو تقسيم حزمة
عند ظهور تكلفة أو مسار ثقيل، مع التحقق من الأثر. اجعل بنية الملفات متوافقة
مع المستودع، وتجنب إعادة تسمية واسعة لا تخدم الطلب.

اختبر المعمارية بمسار ممثل: جلب وعرض وفعل وتحديث وعودة ولغتان، ثم قيّم
وضوح تعديل الميزة. لا تنشئ مخططًا يخالف imports والتنفيذ. عند تغير حاجة
مؤكدة، سجل أثر القرار وغيّره تدريجيًا وفق
[التشخيص والتطور](debugging-and-evolution.md).
