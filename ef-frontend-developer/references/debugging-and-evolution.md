# تشخيص React ومراجعة الكود وتطويره

## Diagnose before rewriting

ابدأ بخطوات إعادة إنتاج محددة والنتيجة المتوقعة والفعلية والإصدارات
والتغيير ذي الصلة. كوّن فرضية، واجمع الدليل الذي يميزها، ثم أصلح السبب
وافحص المسار المتأثر. استخدم logs وReact DevTools وNetwork وProfiler
بحسب المتاح؛ لا تذكر قياسًا أو أداة لم تستخدمها فعلًا.

| العرض المرصود | ما يفيد فحصه قبل الحل |
| --- | --- |
| حلقة تحديث | من يكتب state؟ وهل Effect يغيّر dependency أو مرجعًا يعاد إنشاؤه؟ |
| قيمة قديمة | closure وdependencies وupdater وطلب انتهت صلاحيته |
| فقد مدخل أو focus | key وهوية المكوّن وإعادة التركيب ونسخ بيانات server فوق draft |
| تكرار اتصال/طلب | cleanup وStrict Mode وowner الجلب وquery key |
| بطء إدخال | تكلفة render والـDOM والحساب والاشتراكات وطلبات الشبكة؛ ليست كل إعادة تصيير مشكلة |
| hydration mismatch | أول بيانات ومحتوى من الطرفين وlocale وDOM غير صالح |
| Invalid Hook Call | Rules of Hooks وتوافق React/renderer ووجود نسختين من React |
| بيانات مستخدم سابق | نطاق cache/store وحياة provider وسياسة الخروج وتغير الهوية |
| يعمل محليًا ويفشل بعد البناء | env وbase path وimports وSSR/DOM وESM/CJS وإعداد الوجهة |

لا تضف مؤقتات عشوائية أو suppressions لتغطية race أو خطأ دورة حياة.
ميّز سلوك التطوير من الإنتاج قبل استنتاج تسرب أو تكلفة، مع الاحتفاظ
بالقدرة على كشف الأخطاء في Strict Mode.

## Error handling that matches the failure

Error Boundary تلتقط أخطاء render في الشجرة التي تحميها وفق حدود React؛
ليست catch عامة لكل Promise أو handler أو خطأ خادم. عالج أحداث المستخدم
والعمليات غير المتزامنة في مسارها، واستخدم تكامل الإطار لحدود SSR والمسارات.
مرجع: [React Component / error boundaries](https://react.dev/reference/react/Component).

اجعل fallback يمنح خطوة تعافٍ صالحة، ولا يخفي معلومات تشخيص مهمة عن
الفريق. افصل الخطأ المتوقع من فشل برمجي؛ لا تعرض تفاصيل حساسة في رسالة
المستخدم أو السجلات. في التقارير احتفظ بالمسار والظروف والأثر والتصحيح.

## Behavioral React testing

استخدم أدوات المشروع. افحص reducer أو محول بيانات معقدًا كوحدة عندما
يملك قواعد مستقلة؛ افحص المكوّن بتفاعل المستخدم؛ وافحص الرحلة عبر المتصفح
حيث تتقاطع المسارات والشبكة والترجمة. التفاصيل المشتركة في
[الاختبار والمراجعة](testing-and-review.md).

اختبر الخطر الحقيقي الذي أضافته المهمة، مثل:

- طلب بحث قديم يكتمل بعد الحديث؛ يجب ألا يتغلب على النتيجة الحالية.
- تعديل حقل ثم تغيير اللغة أو وصول refetch؛ يجب الحفاظ على العمل وفق العقد.
- فشل حفظ مع بقاء المدخلات، ثم نجاح لا يترك القائمة والتفاصيل مختلفتين.
- إعادة ترتيب سجلات مع input لكل سجل؛ يجب أن يبقى التعديل مع هوية السجل.
- إغلاق حوار وعودته أو unmount؛ تحقق من focus/cleanup المتعلقين بالتغيير.
- رجوع إلى قائمة أو رابط عميق؛ تأكد من params ومعايير الفرز/البحث المتفق عليها.

حاكِ عند حد adapter أو الشبكة عندما يلزم، مع تحقق من العقد. لا تحاكِ
Hook الاستعلام والمكوّن معًا حتى تختفي المشكلة من الاختبار. MSW يفيد
عندما يحتاج الاختبار سلوك الشبكة؛ fixture بسيطة قد تكفي لمنطق محلي.
استخدم user-event أو ما يكافئه لتفاعل واقعي، وانتظر النتيجة الملاحظة بدل
sleep ثابت. عالج fake timers وتنظيف mocks بين الحالات بعناية.
مراجع: [Testing Library principles](https://testing-library.com/docs/guiding-principles/)،
[MSW](https://mswjs.io/docs/).

لا تختبر تفاصيل framework الداخلية أو تشترط snapshot ضخمًا يتغير لكل
تعديل شكلي. إذا حُقن خطأ متوقع، ميّزه من أخطاء console أخرى. build وtype
check وسلوك المتصفح أدلة مختلفة؛ نجاح أحدها لا يغني عن الآخر.

## Code review and refactoring

ابدأ بالصحة وفقد البيانات والصلاحيات وسلوك المستخدم، ثم الإتاحة والهوية
والأداء المقاس، ثم الصيانة. قدم ملاحظة قابلة للتنفيذ: الموضع، الظروف،
النتيجة غير الصحيحة، وتصحيح مقترح. لا تسمِّ تفضيل تسمية خللًا عالي الخطورة.

في إعادة الهيكلة، حدد السلوك الذي يجب حفظه ونقطة الفصل المطلوبة. غيّر
جزءًا متماسكًا وافحصه؛ أبقِ adapters أو طبقة توافق مؤقتة عند فائدتها مع
حد انتهاء واضح. نقل الملفات وحده لا يثبت تحسن المعمارية. افصل تغيير
السلوك المقصود عن ترتيب الكود ليسهل مراجعته.

## Upgrades and ongoing ownership

للترقية، افحص النسخ وpeer dependencies ودليل migration الرسمي وبيئة
البناء وCI. شغّل codemod مناسبًا عند فائدته، ثم راجع diff؛ الأداة لا
تضمن صحة النصوص والأنواع والسلوك. لا تستبدل الإعدادات العامة أو تفعل
API تجريبية لإكمال ترقية مستقرة دون حاجة متفق عليها.

احفظ شروط الرجوع وحدود التغيير عندما يؤثر الإصدار في التطبيق. اختبر
المسارات التي تتأثر فعلًا، ثم حدّث ما تغير من أوامر ووثائق. احتفظ بقيود
التكامل والاختبارات غير المنفذة ظاهرة؛ لا تعد بالتوافق مع كل منصة نتيجة
تشغيل مشروع واحد.
