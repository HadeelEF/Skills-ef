# فهم المشروع واختيار التقنية

## Start from evidence

افحص أولًا ما يحسم التنفيذ: تعليمات المستودع، حالة Git، ملف الحزم ومديرها
وملف القفل، الإصدارات المثبتة، نقاط الدخول والمسارات، الأنماط والمكونات،
الترجمة، مصدر البيانات، وأوامر التطوير والبناء والفحص. لا تستعرض المستودع
كاملًا إذا كانت الملفات المرتبطة بالتغيير تكفي.

اقرأ نقطة بدء مواصفات UI/UX إن وجدت ثم الشاشة المطلوبة ومعاييرها. افصل
المعلومة المؤكدة عن افتراض قابل للتعديل وعن اعتماد يمنع جزءًا من التنفيذ.
غياب تصميم Figma لا يمنع التنفيذ من مواصفات Markdown واضحة.

اختر مقدار التنظيم بحسب الأثر:

| الحالة | أسلوب مناسب |
| --- | --- |
| إصلاح موضعي | تتبع السبب، عدّل موضعه، افحص السلوك المتأثر والانحدار القريب |
| صفحة أو ميزة جديدة | افهم المسار، أعد استخدام النظام، نفذ الحالات ذات الصلة وافحصها |
| منتج جديد متعدد المسارات | حدد المعمارية وعقود البيانات، نفذ مسارًا ممثلًا ثم وسّع |
| مشروع قائم مضطرب | عالج العائق المثبت، وافصل إعادة الهيكلة اللازمة عن التحسين الاختياري |

لا تجعل عدد الشاشات وحده معيار التعقيد. الأدوار، تزامن البيانات، المدفوعات،
الحفظ، التكاملات، واحتياجات الإتاحة قد تجعل شاشة واحدة أكثر حساسية من موقع تعريفي.

## Choose a fitting stack

التقنية الموجودة وقيد الاستضافة ومهارات الفريق ومتطلبات المهمة تتقدم على
التفضيل الافتراضي. لتطبيق React جديد، ابدأ بتقييم React + TypeScript،
ثم اختر الإطار والتوجيه ونموذج العرض من حاجة المنتج. احترم طلب React
الصريح؛ حجم النموذج الصغير لا يبرر تغييره إلى تقنية أخرى دون داعٍ.

استخدم [اختيار المكتبات](library-selection.md) للمقارنة بين الأطر وإدارة
الحالة والبيانات والنماذج والمكونات والاختبارات، و[العرض والتوجيه](rendering-and-routing.md)
لحدود CSR/SSR/SSG وRSC. المعرفة بـHTML الدلالي وCSS وJavaScript وأدوات
المتصفح أساس التنفيذ حتى عند استعمال مكتبات عالية المستوى.

لا تفصل اقتراح المكتبات عن خطة استخدامها: من يملك البيانات؟ ما الذي
سيبقى محليًا؟ أين تُحمّل الصفحة؟ وكيف يجري الاختبار والنشر؟ مكتبة لا
تعالج حاجة محددة يمكن تأجيلها. مدير الحزم وملف القفل وGit يتبعون المشروع.

عند صيانة Vue أو Angular أو غيرهما، نفذ التغيير ضمن النظام القائم. لا تحول
إلى React لمجرد أن المهارة متخصصة فيه. تحقق من الوثائق الرسمية الخاصة بالإصدار
عند استخدام واجهة غير مألوفة بدل نقل صيغة React إلى إطار مختلف.

## Version and dependency decisions

- اقرأ الإصدار الفعلي وإعداداته قبل نسخ وصفة. تغيّرت مثلًا إعدادات Tailwind
  وواجهات Next.js والتخزين المؤقت وتكوين مكتبات المكونات عبر الإصدارات.
- راجع الوثائق الرسمية للإصدار المستخدم عند اتخاذ قرار يعتمد على هذه الفروق.
  سجل سبب إضافة اعتماد ذي أثر؛ لا تثبت حزمًا لكل احتمال مستقبلي.
- استخدم مدير الحزم وملف القفل القائمين. لا تحدث جميع الاعتمادات لإصلاح مشكلة
  محدودة. في مشروع جديد اختر إصدارًا مدعومًا ومتوافقًا وتحقق منه وقت الإنشاء.
- حافظ على أوامر المشروع واتفاقاته. لا تضف ملف قفل ثانيًا أو تعطل فحص الأنواع
  لإكمال البناء. إذا كان الفشل موجودًا مسبقًا، ميّز أثره عن التغيير المطلوب.
- إعداد monorepo أو microfrontends أو state store عام يحتاج حاجة فعلية؛ لا
  تنشئها تلقائيًا لمجرد توقع نمو المنتج.

## Clarify only material gaps

نطاق المنصات، قواعد الأهلية، شكل API المتاح، وصلاحيات فعل مؤثر قد تتطلب
معلومة من المستخدم. شكل الملفات المحلي، تقسيم مكوّن، أو اختيار فحص مناسب
قرارات تنفيذ عادية. عند عدم توفر خادم، يمكن تنفيذ واجهة ببيانات توضيحية
معلنة وعقد مقترح؛ لا تسمِّها تكاملًا مكتملًا.

مراجع الاختيار: [React](https://react.dev/learn)،
[Next.js](https://nextjs.org/docs/app)، [Vite](https://vite.dev/guide/)،
[Tailwind](https://tailwindcss.com/docs/installation)،
[shadcn/ui](https://ui.shadcn.com/docs). افتح ما يرتبط بالإصدار والمهمة.
