# اختيار المكتبات والمنظومة

## Recommend from constraints

هذه خريطة مفاضلات، وليست preset للتثبيت. افحص الموجود قبل إضافة بديل،
وحدد المشكلة التي ستحلها المكتبة وعقدها مع بقية النظام. اشرح البديل الجدي
فقط عندما يؤثر في القرار؛ لا تعرض قائمة طويلة وتترك الاختيار للمستخدم.

عند قرار جديد ذي أثر، تحقق من النسخة المدعومة وpeer dependencies وتوافق
React والإطار وNode وTypeScript وSSR واللغتين، ومن الترخيص والصيانة عبر
المصدر الرسمي. حجم الحزمة وأثر الاستيراد يُقاسان في بناء المشروع؛ لا تنقل
رقمًا تسويقيًا كقياس محلي. إذا غاب الوصول للمصدر، صرّح بما لم تتحقق منه.

أخرج توصية مختصرة: **الحاجة → الاختيار → سبب الملاءمة → التكلفة/القيد →
البديل عند تغير القيد → طريقة التحقق**. يمكن إدراجها في وثيقة المعمارية
القائمة. لا يلزم تثبيت المكتبة لإجابة سؤال مقارن عنها.

## Framework and routing

| الحاجة | اختيار يدرس وشروطه |
| --- | --- |
| نظام قائم | إطار المشروع وموجهه الحالي؛ تكلفة الترحيل جزء من القرار |
| عرض خادم أو static generation أو إطار يجمع التوجيه والبيانات | Next.js أو إطار React مناسب للبيئة؛ قيّم الاستضافة وحدود الخادم والعميل |
| عميل مستقل يتصل بخادم معروف | Vite مع React وTypeScript خيار مناسب إذا حُسم التوجيه والبيانات والنشر |
| موجه لتطبيق React | React Router أو موجه قائم/ملائم؛ حدد declarative/data/framework mode حسب احتياجك |
| صفحة صغيرة بلا حاجة لتطبيق | أبقِ التنفيذ متناسبًا، مع احترام طلب React الصريح |

Vite أداة بناء ويمكن أن تدخل ضمن إطار؛ ليست مرادفًا لازمًا لـCSR، ووجود
Next.js لا يجعل كل المسارات SSR. لا تجمع موجهين لملكية المسار نفسه.
اقرأ [العرض والتوجيه](rendering-and-routing.md)، ووثائق
[React Router modes](https://reactrouter.com/start/modes)
و[Next.js](https://nextjs.org/docs/app) عند الاختيار.

## State and data ownership

| نوع المشكلة | خيارات مناسبة للتقييم | ما يجب حسمه |
| --- | --- | --- |
| حالة محلية بسيطة | useState، أو useReducer لانتقالات مرتبطة | من يملكها؟ وهل يلزم مشاركتها؟ |
| تمرير إعدادات/لغة أو حالة محدودة ضمن شجرة | Context مع نطاق provider مناسب | معدل التغير ومن يعاد تصييره |
| حالة عميل مشتركة واشتراكات انتقائية | Zustand عند ملاءمته أو store الموجود | selectors، SSR، persistence وعزل الهوية |
| تدفقات عميل تحتاج conventions وإجراءات وتنظيمًا واضحًا | Redux Toolkit عند فائدته أو وجوده | حدود slices وselectors وتكلفة التنظيم |
| سير عمل ذو حالات وانتقالات وحراس معقدة | reducer أولًا حيث يكفي؛ XState عند جدوى نموذج آلة الحالات | تفسير الانتقال والتأثيرات وكيفية اختباره |
| بيانات بعيدة يعاد جلبها وتحديثها | آلية الإطار/router، TanStack Query، SWR أو RTK Query بحسب الموجود | مالك cache والمفاتيح والإبطال وعزل المستخدم |

لا تختَر store عامًا لعلاج بيانات خادم لها cache آخر. إذا كان RTK Query
أو SWR يلبي الحاجة فلا تضف TanStack Query تلقائيًا للمصدر نفسه. وعند
الجمع بين loader وquery cache، حدد من يجلب ومن يعيد التحقق بدل مضاعفة
الطلبات ومسارات الفشل.

مراجع رسمية: [Zustand](https://zustand.docs.pmnd.rs/learn/getting-started/introduction)،
[Redux Toolkit](https://redux.js.org/toolkit/introduction/getting-started)،
[XState](https://stately.ai/docs/xstate)،
[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview)،
[SWR](https://swr.vercel.app/docs/getting-started).

## Forms, interface and product tools

| المجال | التقييم الذي يغير القرار |
| --- | --- |
| النماذج | Native forms/React Actions للملائم؛ React Hook Form عندما تفيد الحقول المركبة وإدارة حالتها؛ تكامل schema مثل Zod حسب العقد |
| الأنماط | CSS Modules أو Tailwind أو نظام المشروع، مع tokens مشتركة؛ تكلفة الصيانة والتوافق أهم من تفضيل syntax |
| المكونات | مكتبة المنتج أولًا؛ primitives مثل [Radix](https://www.radix-ui.com/primitives/docs/overview/introduction) أو [Base UI](https://base-ui.com/react/overview/quick-start) أو shadcn/ui عندما تلائم؛ افحص backend الفعلي وRTL/portals/refs وتركيب المكونات |
| الترجمة | next-intl لتكامل Next.js الملائم، [react-i18next](https://react.i18next.com/) أو نظام مناسب لتطبيق React؛ توحيد المحتوى وURL وSSR حسب المشروع |
| الجداول | جدول دلالي بسيط للمحدود؛ TanStack Table أو المكتبة القائمة للتفاعل المركب؛ virtualization قرار مستقل |
| الحركة | CSS للمحدود؛ [Motion](https://motion.dev/docs/react) أو مكتبة قائمة للتفاعل الذي يبررها، مع reduced motion |
| الرسوم والخرائط والتحرير | اختر بناء على البيانات والإتاحة وRTL والترخيص والحجم وقدرات المنتج المطلوبة، لا على المظهر التجريبي وحده |
| اختبارات المكونات | Vitest/Testing Library أو الأدوات القائمة؛ MSW مفيد لمحاكاة حد الشبكة عندما توجد شبكة في التصميم |
| توثيق مكتبة UI | [Storybook](https://storybook.js.org/docs) عند تطوير مكونات مشتركة ومراجعتها بمعزل عن التطبيق |

هذه خيارات يقيّمها المهندس وليست اعتمادًا رسميًا من EF. تحقق من وثائق
المكتبة المحددة قبل استخدام API أو تثبيت إصدار. استعن بمهارتها المتخصصة
إن توفرت وفادت المهمة؛ غياب plugin لا يعني أن المكتبة نفسها غير قابلة للاستخدام.

## Add and replace dependencies deliberately

افحص ما تضيفه الحزمة ووضعها في runtime/dev وسبب احتياجها. اقرأ تعارض
الإصدارات بدل حلّه بـ`--force` أو `--legacy-peer-deps` تلقائيًا. قد يكون
الإصدار المتوافق أو إزالة dependency غير مستخدم هو المعالجة الصحيحة.

احفظ lockfile القائم واختبر التثبيت والبناء والسلوك المؤثر. عند استبدال
مكتبة، افحص عقودها الموجودة والأصول والأنواع والـCSS والتفاعل، وغيّر
المسار تدريجيًا. لا تخلط ترقية dependencies كبيرة مع إصلاح موضعي بلا ضرورة.
