# TypeScript وعقود React

## Types that describe real states

استخدم إعدادات المشروع. في مشروع جديد مناسب، اجعل strict أساسًا، وحدد
إعدادات modules وJSX والحزم وفق أداة البناء. في مشروع قديم غيّر الصرامة
تدريجيًا ضمن نطاق الترحيل بدل تعطيل الفحص أو فتح موجة تعديلات غير لازمة.

عرّف الحالات والعقود التي تمنع خطأً ملموسًا. discriminated unions نافعة
لـload/mutation state أو props ذات خيارات متنافية، مع تمييز البيانات
القديمة المعروضة أثناء refetch عن التحميل بلا بيانات. لا تجعل الاتحاد
الصارم يستبعد حالة حقيقية يحتاجها المنتج.

استخدم narrowing وفحصًا شاملًا للحالات عندما يساعدان على اكتشاف حالة جديدة
غير معالجة. null وundefined وغياب حقل قد تحمل معاني مختلفة؛ لا تستخدم
truthiness لإسقاط صفر صالح أو سلسلة فارغة مقبولة. `never` مفيد لفحص
الشمولية، وليس لإخفاء مدخل غير معروف.
مرجع: [Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html).

## React component APIs

- استنتج أنواع أحداث DOM وخصائص العناصر من تعريفاتها، وميّز عنصر الرابط
  عن الزر. حافظ على `aria-*` و`data-*` وrefs عند تغليف primitive.
- في controlled props، صمّم العلاقة بين القيمة والتغيير والافتراضي بحيث
  يكتشف المستهلك تضارب الاستخدام. لا تجعل optional لكل شيء حلًا للتباين.
- استخدم generics عندما تحفظ علاقة مفيدة، مثل قيمة الخيار ومعالج اختياره
  أو السجل والأعمدة. مكوّن generic شديد التعقيد قد يصبح أصعب استعمالًا
  من مكوّن صريح؛ اختبر inference في موضع الاستهلاك.
- استخدم utility/mapped/conditional types لاشتقاق علاقة موجودة، مع أسماء
  مفهومة ورسائل خطأ عملية. لا تجعل type-level programming هدفًا بحد ذاته.
- `satisfies` و`as const` يفيدان في ضبط خرائط أو configs مع حفظ معلومات
  الأنواع؛ لا يقومان بفحص بيانات خارجية وقت التشغيل.

مرجع: [Generics](https://www.typescriptlang.org/docs/handbook/2/generics.html)،
[React TypeScript](https://react.dev/learn/typescript).

## Validate trust boundaries

تعامل مع JSON وURL والتخزين المحلي ورسائل cross-window كمدخلات تحتاج
تحققًا مناسبًا. ابدأ من unknown حيث لا يوجد عقد موثوق، ثم تحقق أو حلل
إلى النوع. `as ApiResponse` لا يثبت شكل الاستجابة.

استخدم schema أو عميلًا مولدًا من OpenAPI/GraphQL عندما يفيد مصدر العقد
الفعلي. افصل عقد النقل عن نموذج المجال/العرض إذا اختلف المعنى؛ لا تنسخ
الحقول إلى أنواع كثيرة متطابقة دون حاجة. حافظ على مصدر مرجعي واحد ولا
تعدّل الملفات المولدة يدويًا ثم تفقد التغيير عند التوليد التالي.

حدد معنى المعرف والتاريخ والمبلغ والقيم الغائبة، وطبّق التحويل مرة على
الحد المناسب. لا تحول date-only إلى لحظة زمنية بلا قرار، ولا تحوّل معرفًا
إلى number فتفقد أصفاره. branded types مفيدة عندما تمنع خلط نوعي معرف
بتكلفة مقبولة، ولا تستلزم تحويل كل string إلى نوع جديد.

في التعامل مع الأخطاء، ضيّق `unknown` قبل قراءة `message`، واعرض معنى
مفيدًا للمستخدم بعيدًا عن تفاصيل الخادم. أنشئ عقود أخطاء متوقعة تسمح
بإظهار validation/conflict/unauthorized وفق API الحقيقي.

## Keep type checking meaningful

لا تستخدم `any` أو non-null assertions أو `@ts-ignore` كحل عام لفشل
البناء. إن كان جسر إلى مكتبة سيئة الأنواع ضروريًا، احصره في حد صغير
مع تحقق أو توثيق السبب. افحص mismatched `react`/`react-dom`/`@types/react`
وpeer dependencies قبل تعديل كود سليم لإرضاء تضارب الإصدارات.

تحويل TS إلى JS قد يتم دون type check؛ راجع script الفعلي وشغّل فحص
الأنواع المنفصل حين لا يشمله البناء. اختبر عقود public components أو
الحزم باستهلاك حقيقي، ومع اختبارات types عندما يكون خطر كسرها ملموسًا.
المعيار هو اكتشاف استعمال خاطئ حقيقي، لا زيادة عدد الحيل أو الاختبارات.
