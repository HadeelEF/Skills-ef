# نمذجة النظام وفحص الاتساق عبر حدوده

استخدم عندما تتداخل وحدات وأدوار وبيانات وحالات وتكاملات، أو يُطلب Context/DFD/ERD/State/Sequence/UML أو تحليل أثر عابر للنظام. أنجز النموذج المطلوب فعليًا مع مفتاح وحدود وصلة بالمتطلبات؛ لا تكتفِ بتسمية المخططات. استخدم [حزمة نماذج النظام](../assets/templates/system-analysis-model-pack.md)، واقرأ [تحليل النظم](systems-analysis.md) للعقود والقبول.

## اختر النموذج الذي يحسم الغموض

| الغموض | النموذج المناسب | فحص الاتساق |
|---|---|---|
| حدود النظام والأطراف | System Context | فصل المستخدم/الجهة/النظام والتدفق وملكية الوظيفة؛ لا تتحول الحدود المنطقية إلى قرار نشر |
| مصدر البيانات وتحويلها | DFD منطقي وقاموس تدفقات | حافظ على مدخلات/مخرجات الحدود عند التفكيك؛ لا تجعل سهم البيانات ترتيب تنفيذ أو تعرض مخزنًا ينتج بيانات بلا مصدر |
| مفاهيم العمل وعلاقاتها | Conceptual/Logical ERD أو Domain Model | عرّف الهوية والعلاقة والتعدد والإلزام بمصدر؛ ليست جداول أو فهارس قاعدة بيانات |
| الأفعال المسموحة عبر الزمن | State Model | حدث وحارس ودور وأثر وحالة تالية؛ وجود الحالة في الشاشة لا يبيّن جواز الانتقال |
| ترتيب تبادل ورسائل وفشل | Sequence Diagram | فرّق الطلب وإقرار الاستلام والقبول والتنفيذ والرد، وأظهر البديل والمهلة ذات المصدر |
| هدف فاعل ومساراته | Use Case والنص التفصيلي | حدود النظام والضمانات والبدائل؛ استخدم [مرجع حالات الاستخدام](use-case-engineering.md) |
| قواعد مركبة أو سير عمل | Decision Table أو BPMN | لا تستخدم ترتيب الأسهم ليحسم تنازع سياسة؛ استخدم المراجع المختصة |

سم الرسم توضيحيًا إذا لم تفحصه مقابل الترميز الرسمي. لا تدّعِ مطابقة UML كاملة لأن Mermaid يدعم نوع رسم مشابه؛ اقرأ عناصر المواصفة المستخدمة عند الحاجة الرسمية. لا تنتج جميع النماذج تلقائيًا.

## ثبت لغة المجال وهوية الحقيقة

ابنِ قاموسًا للمفهوم ومعناه وأمثلته ومصدره ومالكه؛ سجّل الألفاظ المتشابهة ذات المعنى المختلف بين الوحدات. ميّز الكيان المستمر عن نسخته وعن الحدث الذي يغيره وعن محاولة تنفيذ حدث. اسم الشخص أو رقم صف مؤقت ليس هوية مستدامة بمجرد وجوده في ملف.

حدد النظام المرجعي لكل خاصية عند اختلاف الملكية، لا لكل كيان فقط: من يكتبها، من يقرأها، كيف تصل نسخة مشتقة، وما تأخرها المقبول بمصدر. استخرج قواعد تفرد وعلاقات وتعدد اختياري/إلزامي من السياسة؛ وسم الاستنتاجات التي تحتاج تأكيدًا. لا تفترض حذفًا متسلسلًا عند حذف أصل أو تطابق شخصين لتشابه الاسم.

افصل حالة الأعمال عن حالة التكامل/المزامنة وعن حالة مهمة بشرية. قد يكون الطلب معتمدًا لكن لم يُنفذ خارجيًا، أو أُرسلت الرسالة دون معرفة أثرها؛ لا تختزلها في «مكتمل». استخدم نماذج حالة منفصلة مترابطة عندما يكشف ذلك الفرق، لا تعدادًا هائلًا لكل تركيب ممكن.

## الزمن والنسخ وثوابت الأعمال

لكل فعل مؤثر حدد نسخة البيانات والسياسة التي يحكم عليها، وما إذا كان القرار يستخدم لقطة محفوظة أم قيمة حالية، وتاريخ النفاذ مع المنطقة الزمنية والتقويم. لا تختر حكمًا رجعيًا على معاملات سابقة من تحديث جدول مرجعي جديد. عالج البيانات المتأخرة والتصحيح بأثر واضح في التقارير والحقوق والتكامل.

صغ الثابت بصيغة يمكن نقضها بمثال: ما الذي يجب أن يبقى صحيحًا قبل وبعد فعل؟ اربطه بمصدر أو صفة اقتراح. أمثلة تعليمية مقترحة: لا ينتج عن محاولتين لنفس أمر الأعمال أثر مكرر، ولا يعتمد مفوض بعد انتهاء تفويضه. ليست هذه قواعد مشروع ما لم تثبت مصادره؛ كيفية ضمانها تنفيذًا للمعماري والمطور.

اختبر معاملات تتعارض على نفس الحد/الحصة/السجل: ما وحدة التعارض وما نتيجة الطلب الفائز والخاسر ومن يستطيع إعادة المحاولة؟ «آخر حفظ يفوز» خيار سلوكي ذو أثر، وليس تفصيلًا تقنيًا محايدًا. رجوع استجابة قديمة لا ينبغي أن يُفهم تلقائيًا كتراجع للحالة الحديثة؛ سياسة قبول الحدث وترتيبه تحتاج تعريفًا.

## عقد حدود النظام

| البعد | ما يجب حسمه أو إعلانه مجهولًا |
|---|---|
| معنى العملية | أمر يطلب تغييرًا أم حدث يعلن حقيقة أم استعلام؛ المحفز والفاعل والهدف |
| البيانات | المعنى ووحدة/عملة/تقويم وقيم null والغياب والصفر، الإلزام والتعدد ونسخة المرجع |
| النجاح | نجاح النقل أم قبول المعالجة أم تحقق نتيجة الأعمال؛ ما يراه المستخدم في كل مرحلة |
| هوية التبادل | هوية الحالة والأمر والمحاولة والحدث ونسخة البيانات عند الحاجة؛ لا تخلط إعادة إرسال بعمل جديد |
| الفشل والالتباس | رفض أعمال، خطأ تحقق، عدم تصريح، تعذر خدمة، نتيجة غير معروفة، وأثر جزئي |
| التعافي | سياسة استعلام/إعادة محاولة/تعويض/تدخل ومصالحة بمصدر؛ لا تحول مهلة الاتصال إلى رفض أعمال |
| التغيير | توافق المستهلكين ومعنى الحقول والحالات، سريان النسخة والطلبات الجارية ودليل قبول الطرفين |

في معالجة دفعة حدد هل وحدة القبول ملف أم صف أم مجموعة ذات علاقة؛ وهل النتيجة كلية أم جزئية وما مصير التكرار والرفض والمصالحة. لا تعمم نتيجة إجمالية على كل سجل أو تعد صفرًا من الأخطاء نجاحًا إذا لم تُعالج الصفوف أصلًا. استخدم [الانتقال والمصالحة](brownfield-and-transition.md) إذا كان ذلك ضمن ترحيل.

## افحص القنوات والجودة وإساءة الاستخدام

تتبع وظيفة واحدة عبر واجهة وAPI وتصدير وتقرير وإشعار ورابط ملف ومعالجة خلفية عند وجودها. صلاحية الزر لا تكفي؛ حلل نطاق المؤسسة/المساحة/السجل/الحقل، والتفويض والسحب وتغير الدور، وما يظهر من إجماليات أو وجود سجل لغير المخول. لا تضف multi-tenancy إذا لم يوجد بالمشروع، لكن لا تسقط حدًا مثبتًا عند نقل الفعل لقناة أخرى.

صغ حالات منع وإساءة استخدام متناسبة: مستخدم يخمن معرّف سجل، مُنشئ يحاول اعتماد عمله خلاف السياسة، طلب مكرر، ملف أو قيمة إدخال غير صالحة. اربطها بثابت أو قيد ونتيجة قابلة للاختبار دون اختراع مواصفة أمنية ملزمة. تفاصيل آليات الحماية لدى المختص؛ المتطلب يحدد أثرًا ومنعًا يمكن التحقق منه.

للجوال أو العمل غير المتصل عند دخوله النطاق: حلل حداثة النسخة وحالة الإرسال والموافقة قبل الفعل ومصير الكتابات المعلقة عند تغير السياسة/الصلاحية. لا تعتبر «سيزامن لاحقًا» سياسة لحل تعارض. لميزة AI ضمن المنتج: حدد مهمة القرار وحدود السلطة والمصادر المسموحة، الامتناع أو المراجعة البشرية، الخطأ المقبول ومجتمع التقييم وأثر اللغة والفئات وتغير النموذج؛ لا تجعل جودة عينة واحدة ضمانًا لكل حالة أو تسمح للمقترح بتغيير سجل أعمال بلا تفويض.

## مشي سيناريو مترابط ثم تسليم

اختر حالة ناجحة وحدًا ورفض صلاحية وفشلًا جزئيًا أو حدثًا متأخرًا بحسب المخاطرة. تتبع الأدوار والكيانات ونسخها والحالات والقواعد والرسائل والمخرجات، ثم طابق النتيجة عبر الرسم وجدول الانتقالات وUC/Story والقبول وRTM. لا تكتفِ بسلامة كل نموذج منفردًا.

مثال تعليمي: بوابة أرسلت أمر حجز ولم تتلق ردًا؛ النظام الخارجي نفذه، ثم وصل رد متأخر بعد محاولة المستخدم مجددًا. التحليل يميّز غموض نتيجة المحاولة عن فشل الحجز، ويتطلب قرارًا لهوية الأمر والتكرار والمصالحة قبل افتراض إنشاء حجز آخر أو إلغائه. لا يفرض المثال API أو queue أو قاعدة بيانات.

سلّم الحد واللغة والعقود ومعرّفات النماذج والمصادر وحالات القبول والفجوات مع مالك كل قرار. استخدم مستويات جاهزية منفصلة: يمكن تحليل الواجهة أو بناء عقد تمثيلي مع بقاء التكامل/الإطلاق غير جاهز. أحل التصميم التقني إلى معماري الحل مع خياراته وأسئلته، ولا تملأ فراغ الأعمال بتقنية تختارها نيابة عنه.
