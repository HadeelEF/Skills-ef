# العمل المهني داخل Linear

اقرأ هذا المرجع عند طلب بناء Backlog في Linear أو تدقيقه أو تحديثه أو تحويل وثائق إليه. اقرأ معه مرجع المنتج عند بناء المحتوى؛ لا تجعل توفر الاتصال شرطًا لإنجاز التحليل المستقل. هذه إرشادات تشغيل أصلية مبنية على الوثائق الرسمية ومخططات الأدوات التي فُحصت في 2026-10-04؛ أعد اكتشاف القدرات والحقول وقت الاستخدام.

## تحديد نمط العمل

- **تحليل/تجهيز:** إذا طلب المستخدم تصميم Backlog أو خطة Linear، أنتج المحتوى وخريطة التحويل؛ لا تعتبر اسم Linear وحده تفويضًا للكتابة في حسابه.
- **تنفيذ:** طلب إنشاء/تحديث العناصر في مساحة محددة يجيز الخطوات اللازمة ضمن نطاقه. اقرأ الموجود، جهز التغييرات ثم نفذها؛ لا تطلب موافقة مكررة لكل تذكرة. احصر أي غموض مؤثر أو فعل خارج التفويض، وواصل المستقل.
- **تدقيق:** ابدأ بقراءة النطاق وتقرير الفروق؛ عند طلب الإصلاح أصلح ضمن التفويض وأعد القراءة للتحقق.
- **اتصال غير متاح:** سلّم Backlog قابلًا للاستخدام وخريطة الحقول وسجل ما لم يُنفذ. لا تقل «تمت المزامنة» ولا تختلق معرفات أو روابط. لا تعد باستيراد CSV شامل دون التحقق من دعم الحقول والعلاقات فعليًا.

## تمثيل المنتج دون فرض هيكل

| معنى تحليلي | تمثيل Linear محتمل | قاعدة الاختيار |
|---|---|---|
| هدف استراتيجي يضم مشاريع | Initiative | عند وجود هذا المستوى وحاجة فعلية؛ لا يلزم كل منتج أو تغيير |
| نتيجة تسليم من عدة عناصر | Project | استخدم المشروع القائم الملائم؛ قد يجمع فرقًا متعددة بحسب إعداداته |
| نقطة تقدم ذات معنى داخل مشروع | Milestone | لها معيار اكتمال؛ ليست حالة تنفيذ أو تاريخًا إلزاميًا |
| Epic/Feature | Project أو Milestone أو Parent issue أو تجميع موثق | اختر حسب الحجم والمعنى وعرف الفريق؛ لا تفترض كائنًا ثابتًا باسم Epic أو تحويل كل Epic إلى مشروع |
| Story / Bug / Spike / Enabler | Issue | ضع نوع العمل بوصفه أو التصنيف المتاح؛ لا تفترض حقل Issue Type أو تنشئ Labels جديدة دون حاجة وتفويض |
| أجزاء عمل تحت عنصر جامع | Sub-issues | استخدم parentId بعد معرفة الأب، واحفظ قيمة القصة والقبول والتتبع |
| فترة عمل الفريق | Cycle | ليست إصدارًا ولا أولوية؛ لا تضف العمل إليها كالتزام دون مدخلات أو تفويض الفريق |
| تصنيف/منظور | Label / View | لا تستبدل متطلبًا أو اعتمادًا أو حالة، ولا تفترض وجود أداة لإنشاء View |

النموذج أعلاه توصية اختيار وليس إلزامًا من Linear. تحقق من الميزات المتاحة للخطة والصلاحيات والإعدادات؛ لا تفترض تفعيل Initiatives أو Triage أو Cycles أو Releases. افصل Release الفعلي عند توفره عن Milestone وCycle، ولا تدّع النشر من اكتمال التذاكر.

## اكتشاف السياق والأدوات

1. اكتشف أدوات Linear المتاحة واقرأ مخطط كل أداة ستستخدمها؛ أسماء الأدوات التالية أمثلة للموصل المفحوص وليست ضمانًا دائمًا. لا تستخدم حقلًا لم يرد في المخطط ولا تستبدل قدرة غير متاحة بادعاء تنفيذ.
2. احسم Workspace وTeam وProject من الروابط/المعرفات والسياق والقراءة. استخدم القراءة المستهدفة قبل السؤال؛ إذا تشابهت أسماء جهات مختلفة وأثر ذلك في الكتابة، اطلب تحديد الهدف ولا تخمّن.
3. اقرأ فرق النطاق ومشاريعه والعناصر القائمة، ثم حالات كل فريق والـLabels والقوالب والـMilestones وCycles عند استخدامها. تحقق من هوية المكلف/المالك الفعلية قبل الإسناد. لا تسند العمل أو تملأ estimates/due dates تلقائيًا.
4. اجلب الصفحات اللازمة عبر cursor؛ راعِ Triage والعناصر المكتملة والمؤرشفة في بحث التكرار، بحسب ما تسمح به الأداة. وضح نطاق البحث وحدوده؛ نتيجة صفحة أو استعلام نصي واحد لا تثبت عدم وجود عنصر.
5. اقرأ العنصر الكامل والعلاقات قبل تحديثه؛ نتائج القوائم المختصرة قد لا تتضمن الوصف أو العلاقات. تحقق من الوضوح وسلطة المصدر قبل نسخ مادة حساسة من وثيقة خاصة إلى مشروع أوسع رؤية.

| الغرض | أدوات مفحوصة وكيف تستخدم |
|---|---|
| الاكتشاف | list_teams / get_team، list_projects / get_project، list_issue_statuses، list_issue_labels، list_templates / get_template، list_users عند الإسناد |
| البحث والقراءة | list_issues مع team/project/query/cursor/includeArchived/fields وفق المخطط؛ get_issue مع includeRelations عند أثر العلاقات |
| التخطيط | list_milestones / list_cycles / list_initiatives عند استخدامها؛ تحقق أن Cycle للفريق وMilestone للمشروع الصحيح |
| الكتابة | save_issue: وجود id تحديث، غيابه إنشاء؛ save_project وsave_milestone وsave_document وغيرها فقط عند حاجة وتفويض ودعم |
| التحقق من الخاصية | search_documentation والمصادر الرسمية؛ وثيقة المنتج لا تضمن أن الموصل يعرض الخاصية |

لا تنشئ Team أو workflow أو labels أو إعدادات مساحة جديدة لمجرد غياب تنظيمك المفضل. قدم إعدادًا مقترحًا فقط إذا احتاج العمل قرار تكوين خارج النطاق. لا تستخدم share_issue أو التعليقات أو mentions أو نشر تحديثات وإرسال رسائل إلا عند طلبها صراحة. افحص أثر الأتمتة ذات الصلة: القوالب وTriage قد تضبط الحالة، وعلاقة الأبناء قد تقترن بإغلاق تلقائي؛ لا تعتبر القيم التي طلبتها هي النتيجة المحفوظة دون قراءة.

## المطابقة والتتبع ومصدر الحقيقة

احتفظ بثلاث هويات منفصلة: معرّف المتطلب/عنصر Backlog المستقر، ومعرّف Linear الظاهر، ومعرّف الكائن الذي تعيده الأداة. استخدم returned id في التحديث واربط الرابط الفعلي؛ لا تصنع URL أو تحسب الرقم التالي. نقل عنصر إلى فريق آخر قد يغير معرّفه الظاهر وخصائصه؛ لا تنفذه ضمن تنظيف شكلي.

ابدأ المطابقة بالمعرف/الرابط الموجود، ثم مفتاح مصدر ثابت داخل الوصف إن كان العرف مناسبًا، ثم المصدر والمشروع والفريق والسلوك. عنوان مشابه مجرد مرشح، وليس دليل تكرار. عند تعدد المرشحين سجل تعارضًا؛ لا تدمج أو تحذف أو تنشئ نسخة ثالثة قبل حسم المطابقة. استخدم مثلًا `Source key: product-code/US-...` بوصفه مفتاح تتبع أصليًا إن احتجت؛ ليس حقل API ولا مفتاح idempotency يضمنه Linear.

حدد المرجع لكل معلومة: الوثيقة المعتمدة للسياسة/المتطلب؛ Linear لترتيب وحالة التنفيذ حين يكون اتفاق المشروع كذلك؛ معايير القبول في موضع واحد محدد وروابط من الآخر. لا تنشئ مزامنة ثنائية تعيد كتابة المصدرين من دون ملكية حقول وقاعدة تعارض. سجل المصدر وإصداره وآخر قراءة والتغير المقترح؛ وقت التعديل الأحدث لا ينسخ سلطة الاعتماد.

## إعداد خطة تغييرات قابلة للتنفيذ

جهز باختصار لكل عنصر: create/update/no-change/needs-decision، المصدر والمفتاح، الهدف الموجود أو المقرر، الحقول القديمة والجديدة، الاعتماديات ومبرر التغيير. استعمل قالب Linear أو ردًا مختصرًا للتغيير الصغير. لا تجعل الخطة بوابة موافقة إذا كان التنفيذ نفسه مصرحًا؛ نفذ المستقل بعد إعدادها.

- **الحالة:** استخدم حالة حقيقية من الفريق ومعرّفها عند احتمال اللبس؛ لا تفترض أسماء Ready أو Done. حالة التذكرة لا تمنح المتطلب اعتمادًا.
- **الأولوية:** تحقق من مخطط الأداة. القيم المفحوصة للـIssues: 0 بلا أولوية، 1 Urgent، 2 High، 3 Medium، 4 Low. لا تعكس ترتيب الأرقام، ولا تحول Must إلى Urgent أو RICE إلى priority آليًا. لا تضع Urgent لمجرد رغبة عامة؛ قد يرسل إشعارات. أبقِ ترتيب الأعمال وتبريره مستقلين عن الفئة.
- **الترتيب داخل الفئة:** تغيير priority لا يثبت تغيير الترتيب اليدوي. إذا لم يعرض الموصل حقل ترتيب، احتفظ بالترتيب المقترح في السجل وبيّن أن ترتيب لوحة Linear لم يُعدل.
- **الحقول:** اترك غير المصرح بتغييره كما هو. لا تمرر null أو [] إلا بقصد مسح مفهوم ومصرح. للـLabels استخدم add/remove عند دعمها بدل قائمة استبدال تمحو تصنيفات الفريق.
- **الوصف:** عدل مقطعًا محددًا بـpatch إذا دُعم وكان مرساه فريدًا. إن لزم استبدال الوصف فاقرأ أحدث نص وادمج التغيير مع حفظ إضافات الآخرين. لا تفترض وجود حماية شرطية من التزامن؛ إذا تغيرت الدلالة فاعد المقارنة قبل الكتابة.
- **العلاقات:** عندما يحتاج B إلى A، استخدم blockedBy=[A] على B أو blocks=[B] على A وفق المخطط، دون إضافة اتجاهين متعاكسين. relatedTo ليست مانعًا. لا تستخدم duplicateOf لمجرد تشابه؛ قد يغير حالة العنصر. تحقق من معنى الحقول الإضافي/الاستبدالي ولا تمحُ علاقات قائمة بالافتراض.

## التنفيذ والتحقق والاستئناف

1. نفذ الاعتماديات بالترتيب: إعادة استخدام/إنشاء الحاوية الضرورية، Milestones عند الحاجة، العناصر الآباء، الأبناء، ثم العلاقات بعد معرفة IDs. لا تكرر كل مستويات الهيكل؛ إنشاء عنصر منفرد قد يكون كل المطلوب. اجعل الكتابات المعتمدة على بعضها متتابعة.
2. سجل لكل استجابة معرفها ورابطها والحقول المحفوظة ووقت العملية ونتيجتها. لا تعتبر الدفعة معاملة ذرية؛ قد ينجح بعضها فقط. احفظ سجل الاستئناف في الموقع المصرح عند طول العمل.
3. عند مهلة/انقطاع بعد create أو نتيجة ملتبسة: ابحث عن المفتاح والمصدر في النطاق الصحيح وافحص العنصر قبل إعادة المحاولة. «لم يصل الرد» لا يثبت الفشل. إذا بقيت النتيجة مجهولة أوقف إنشاء هذا العنصر وواصل المستقل؛ لا تنشئ نسخة احتياطية مكررة.
4. عند خطأ تحقق صحح الحقول بعد قراءة الخطأ؛ عند نقص صلاحية لا توسع الصلاحيات أو تبدل الحساب بنفسك. عند تحديد معدل اتبع الإرشاد المتاح وأعد المحاولة بصورة محدودة. لا تدّع وجود معاملة أو rollback أو idempotency غير موثقة.
5. اقرأ النتائج الفعلية بعد الكتابة: الهوية والفريق والمشروع والحالة والوصف/القبول والتصنيفات والأب وMilestone/Cycle والعلاقات المتأثرة. طابق كل الحقول المعدلة؛ نجاح الأداة وحده لا يثبت المحتوى. تحقق أيضًا من بقاء الحقول القائمة التي كان الاستبدال يهددها.
6. صحح الفروق الداخلة في التفويض ثم أعد فحصها. عند فشل علاقة بعد نجاح إنشاء العناصر، أعد العلاقة فقط بالمعرفات القائمة. لا تحذف ما نجح لتعويض فشل جزئي بلا تفويض.
7. سلّم عدد الإنشاء/التحديث/دون تغيير/المعلق/الفاشل وروابط العناصر الفعلية، وما تحقق بقراءة وما بقي غير مؤكد. ميّز «جاهز في مستند» عن «حُفظ في Linear وتمت قراءته» وعن «اختُبر سلوكه في النظام».

## مراجعة سيناريوهات التشغيل قبل دفعة مؤثرة

اختر السيناريو ذي الأثر فقط، واستخدم مشروع اختبار إذا كان إنشاء عناصر تجريبية مصرحًا؛ تحديث المهارة وحده لا يجيز الكتابة في حساب حقيقي. عند محاكاة الاستجابات أعلن أنها محاكاة، ولا تجعلها إثبات تشغيل حي.

| الحالة | تصرف قابل للتحقق |
|---|---|
| وصف عدله زميل منذ القراءة | أعد قراءة النص وادمج المقطع المقصود مع حفظ الإضافات؛ لا تستبدل النسخة القديمة |
| مهلة بعد create مع نجاح محتمل | ابحث بالمفتاح والنطاق ثم اقرأ المرشح؛ لا تُعد الإنشاء قبل معرفة النتيجة |
| عنصران متشابهان من جهتين | قارن مصدرهما وسلوكهما ونطاقهما؛ لا تستخدم duplicateOf تلقائيًا |
| نجحت العناصر وفشلت علاقة | أعد العلاقة فقط بالهويات القائمة، ثم اقرأ اتجاهها وحفظ العلاقات السابقة |
| مطلوب ترتيب/حقل لا تدعمه الأداة | نفذ المدعوم وقدم الترتيب المتبقي كاقتراح؛ لا تدع أنه حُفظ على اللوحة |

## تشغيل Backlog قائم ومتابعته

استخدم منظورًا يخدم القرار: الوارد الذي يحتاج فرزًا، أعلى العناصر مع أسئلة Refinement، المحجوب بعلاقة وسبب، الإصدار/المشروع، أو فجوات التغطية. إن لم تدعم الأدوات إنشاء Views قدم وصف الفلتر ولا تدّع إنشاءه. لا تغيّر إعدادات Triage أو الأرشفة لتجاوز حدود الرؤية.

في التنقيح: طابق المقترحات مع العمل الجاري لتفادي الازدواج، حافظ على تقدير الفريق ومالكه وتعليقاته، أصلح القبول والروابط ضمن التفويض، وحدّث أثر التغيير على العناصر المتأثرة. عند طلب تنظيف التكرار حدد العنصر المرجعي وسبب المطابقة ومصير التعليقات والمرفقات قبل أي دمج مصرح. لا تمسح العناصر القديمة أو تغلقها لمجرد عمرها.

المصادر الرسمية وتاريخ التحقق في فهرس المصادر المهنية. راجع الخاصية المعنية فقط عند الحاجة؛ إذا تعارض وصف عام مع مخرجات الحساب أو مخطط الأداة، سجل الفرق وتحقق بدل افتراض سلوك ملائم.
