## Frame

استخدم ما ورد في المحادثة والملفات والمشروع قبل طلب معلومات إضافية. كوّن
فهمًا مختصرًا للنتيجة المطلوبة: من المستخدم، ماذا يريد إنجازه، ما المخرج
المطلوب الآن، وما القيود التي يمكن أن تغيّر الحل؟

قيّم عند الحاجة: اختلاف الأدوار، ترابط المهام، البيانات والصلاحيات، حساسية
الأخطاء، النظام القائم، الأجهزة، قنوات الدخول، اللغتين، الاعتمادات والموعد.
قد تكون شاشة اعتماد واحدة أعقد من موقع تعريفي متعدد الصفحات. لا تحول التقييم
إلى درجة رقمية اعتباطية أو استبيان موحد على كل عميل.

بيّن في العمل الكبير، باختصار: الهدف، النهج المختار وسببه، المخرجات،
والافتراضات المؤثرة. هذا جزء من موجز المشروع، ولا يستلزم مستندًا مستقلًا.

## Depth

| طبيعة الطلب | العمل المناسب مبدئيًا | متى يتوسع؟ |
| --- | --- | --- |
| نص أو زر أو مكوّن محدد | فحص السياق وتعديل موضعي مع أثره على اللغتين والحالات | عندما يتغير مكوّن مشترك أو مسار خدمة |
| صفحة واضحة المتطلبات | ترتيب المحتوى والتكوين والتفاعل والتجاوب مباشرة | عندما توجد رحلة متعددة الخطوات أو قاعدة عمل مفقودة |
| تحسين منتج قائم | تتبع المهمة الحالية وتحديد الاحتكاك والأثر ثم تصحيح مركز | عندما يكمن السبب في التنقل أو نموذج المعلومات |
| خدمة أو منصة متعددة الأدوار | مهام وأدوار، هيكلة معلومات، مسارات مكتملة، نظام مشترك ومواصفات | بحسب الاعتمادات والتكاملات الفعلية |
| فكرة مبكرة غير محسومة | تحديد الفرضية المهمة وبناء تصور أو استكشاف محدود | عندما تتوفر أدلة تكفي لتفصيل الحل |
| مراجعة تنفيذ | مقارنة مواضع فعلية بالمواصفات والهوية وإتمام المهمة | عندما يظهر عيب مشترك يتكرر عبر الشاشات |

الصفوف أمثلة لاتخاذ القرار وليست بوابات موافقة. لا تفرض Personas أو Journey
Map أو Wireframes أو Design Sprint عندما لا تغيّر نتيجة المهمة. استخدم أسماء
المناهج عندما تساعد على تفسير العمل، ثم نفّذ ما يتطلبه المشروع.

## Evidence

اختر طريقة الاستكشاف انطلاقًا من سؤال تصميمي محدد:

| السؤال | دليل أو طريقة مفيدة | حدود النتيجة |
| --- | --- | --- |
| أين يتعثر المستخدم؟ | مشاهدات فعلية، تسجيلات مسموحة، طلبات دعم أو تحليلات متاحة | وصف المشكلة لا يثبت سببها وحده |
| هل التصنيف مفهوم؟ | تحليل المهام؛ اختبار شجرة أو فرز بطاقات إذا أمكن | التصنيف المقترح فرضية حتى يختبر |
| هل المسار قابل للإتمام؟ | مرور معرفي خبير، أو اختبار استخدام بمهام واقعية | مراجعة الخبير ليست بحثًا مع مستخدمين |
| هل الاتجاه البصري مناسب؟ | شاشة ممثلة أو نموذج تفاعلي وفحص للغتين | رأي أصحاب المصلحة يختلف عن أداء المستخدم |
| هل التغيير حسّن النتيجة؟ | مقياس مرتبط بالمهمة وخط أساس وبيانات فعلية | لا تنسب تحسنًا رقميًا لتوقع تصميمي |

عند غياب الأبحاث، اعمل بفرضيات واضحة ومراجعة مهنية. لا تخترع أشخاصًا بحثيين
أو اقتباسات أو نسبًا. عرّف أدوارًا مؤقتة مرتبطة بالمهام عند الحاجة، وسمّها
افتراضات. إذا طُلب بحث أو اختبار، حدد المشاركين والمهام والدليل المراد جمعه؛
إجراء تواصل خارجي أو تشغيل دراسة يتطلب نطاقًا وصلاحيات فعلية.

## Decisions

| نوع النقص | التصرف |
| --- | --- |
| قرار تصميم معتاد | اختر حلًا مناسبًا وواصل؛ سجل السبب إذا كان مؤثرًا |
| افتراض قابل للمراجعة | اذكر الافتراض وما يتأثر به؛ حدّثه عند ظهور الدليل |
| قاعدة عمل تغيّر الاستحقاق أو الصلاحيات أو النتيجة | اطلب المعلومة المحددة وأكمل بقية النطاق |
| أصل أو قدرة أداة غير متوفرة | بيّن الجزء المتأثر، وقدّم ما يمكن إنجازه دون ادعاء اكتماله |

لا تجعل المستخدم يختار مقاسات الأزرار أو كل تفصيل بصري. عند وجود مفاضلة
حقيقية، قدم توصية وسببها وتكلفتها: مثل كثافة جدول العمل مقابل سهولة القراءة،
أو إكمال نموذج في صفحة مقابل تقسيمه إلى خطوات.

الطلب الجديد يوجّه العمل القائم. عند تعديل قرار مشترك، حدد الشاشات المتأثرة
وحدّث المرجع المعني. لا توسع إعادة التصميم إلى أجزاء مستقرة دون سبب مرتبط
بالطلب. احترم نقاط المراجعة التي يحددها المستخدم، وأكمل العمل المأذون الذي
يجعل نتيجة المراجعة ملموسة.

## Progress

ابدأ بمسار مفيد مكتمل عند اتساع المشروع. حسْم التنقل ونموذج المحتوى ومكوّن
ممثل مبكرًا قد يمنع تكرار قرارات غير متسقة. استخدم تخطيطًا أوليًا أو نموذجًا
مرئيًا عندما يجيب عن سؤال فعلي؛ لا تنتج نسخة منخفضة الدقة لمجرد وجود مرحلة.

عندما يكون الوقت محدودًا، قدّم المهمة الأساسية ومعالجة الفشل المؤثر، وبيّن
ما تأجل وأثره. إذا كان المطلوب تسليمًا كاملًا، لا تسمِّ عينة محدودة تنفيذًا
لكل النطاق. تكون النهاية بتحقق المخرج المطلوب ووضوح الاعتمادات المتبقية،
وتوثّق وفق [التسليم للمطور](developer-handoff.md).
