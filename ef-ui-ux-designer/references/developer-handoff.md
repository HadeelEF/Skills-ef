## Package

اجعل المخرج قابلًا للفهم والتنفيذ بواسطة Codex أو Claude Code أو ChatGPT
أو Claude أو مطور بشري في جلسة جديدة. يستلم المطور متطلبات وتجربة وقرارات
واجهة واضحة؛ يجب ألا تعتمد معلومة حاسمة على ذاكرة هذه المحادثة.

استخدم بنية المشروع القائمة. للطلب الصغير يكفي مستند واحد مركز أو تعديل
المواصفات الموجودة. في المشروع الكبير يمكن توزيع الأدوار التالية؛ الأسماء
أمثلة، ولا تنشئ ملفات أو أقسامًا فارغة لمجرد إكمالها:

| دور المستند | اسم مقترح | المحتوى |
| --- | --- | --- |
| نقطة البدء | `design/index.md` | الهدف والنطاق والمنصات واللغات وترتيب القراءة والتنفيذ والاعتمادات |
| التجربة | `design/ux.md` | المهام والأدوار والتنقل والمسارات وقواعد العمل المعروفة |
| النظام البصري | `design/ui-system.md` | الرموز وقيمها والأدوار والمكونات المشتركة والتجاوب |
| الشاشات | `design/screens/<screen-id>.md` | التكوين والمحتوى والتفاعل والحالات الخاصة بالشاشة |
| النصوص | `design/content.md` | مفاتيح المحتوى بالعربية والإنجليزية والمصطلحات والتنسيق |
| القبول | `design/acceptance.md` | شروط إتمام المهام ومطابقة التصميم وفحوص اللغتين |

ادمج النصوص أو القبول في ملف الشاشة عندما يكون ذلك أوضح. المنتج الصغير
لا يحتاج هذا التفكيك. وثائق المشروع الناتجة منفصلة عن مجلد هذه المهارة.

## Baseline

امنح كل قرار تعريفًا واحدًا، ثم أحِل إليه من الشاشات. استخدم معرفات ثابتة
للمكونات والشاشات والحالات والنصوص عندما تفيد في منع الالتباس.

ميّز عند الحاجة بين:

- **متطلب مؤكد:** له مصدر من المستخدم أو المشروع أو وثيقة موثقة.
- **قرار تصميم:** اختيار للمشروع مع سبب موجز إذا كان مؤثرًا.
- **افتراض:** قابل للمراجعة مع بيان مواضع تأثيره.
- **اعتماد مفتوح:** معلومة أو قدرة أو أصل مفقود وما يمنعه تحديدًا.

سجّل اسم وإصدار مرجع الهوية المستخدم، والقيم المختارة ومراجعها، وقرارات
المنتج الدلالية، والأصول الفعلية. تنقل المشروع بين الأدوات لا يقتضي تكرار
مصادر متنافسة للقيم. إذا تغير المرجع لاحقًا، راجع أثره على خط أساس المشروع.

وثّق المكتبة والمنصة الحالية حين تكونان معلومتين. صياغة UI لا تُلزم المطور
بإطار أو مزود مصادقة أو استضافة لم يطلبه المشروع. فصّل قيود التصميم،
واسمح للمنفذ بحسم التفاصيل التقنية ضمنها.

## Screen specification

استخدم الحقول اللازمة من العقد التالي، واحذف غير المنطبق:

1. **الهوية والهدف:** معرف الشاشة، المسار إن عُرف، المستخدم والمهمة،
   نقاط الدخول والخروج، والشروط المرتبطة بالأدوار.
2. **التكوين:** ترتيب القراءة، الهيكل المشترك، الأقسام وتسلسل أهميتها،
   الأعمدة والعروض والقيود والمسافات والمحاذاة ومراجع المكونات.
3. **التفاصيل البصرية:** رموز الخط والحجم والوزن وتباعد الأسطر، أدوار
   الألوان وقيمها المرجعية، الحدود والأشكال والأيقونات والأصول ومواضعها.
4. **المحتوى والبيانات:** النص الفعلي باللغتين أو مفاتيحه، الحقول والوحدات
   والتنسيق والاقتطاع والمحتوى الطويل، وحالة البيانات الحقيقية أو التوضيحية.
5. **الإجراءات والحالات:** المحفز والنتيجة والانتقال والفشل والتعافي،
   والانشغال والفراغ والحالات الأخرى التي يمكن أن تحدث في هذه الشاشة.
6. **التكيف والإتاحة:** تغير التخطيط عبر المساحات، اختلاف RTL/LTR،
   التركيز ولوحة المفاتيح واللمس والأسماء الميسرة وتبديل اللغة.
7. **القبول والاعتمادات:** شروط قابلة للفحص، والمعلومات التي ما زالت
   مطلوبة وأثرها على التنفيذ.

المقاس الثابت له قيمة ووحدة، والسلوك المرن له حدود وقاعدة واضحة.
عبارة «نفس الهوية» لا تعوض تحديد الأصل والدور اللوني والخط. لا تجعل
المطور يستنتج كل قيم النظام من صورة أو اسم نمط.

لتغطية اللغتين، عرّف السلوك المشترك مرة، ثم الفروق المقصودة. يجب أن يكون
لكل نص وظيفي ضمن النطاق صياغة عربية وإنجليزية أو اعتماد محدد يمنع اعتماد
النص. لا تترك عبارة «تُترجم لاحقًا» بديلًا عن تسليم المحتوى المطلوب.

## Interaction contract

للأفعال المركبة، استخدم جدولًا من هذا النوع مع بيانات المشروع:

| العنصر | ما يحتاجه المنفذ |
| --- | --- |
| المحفز | نقر أو إدخال أو انتقال، مع حالة البداية والشروط |
| الاستجابة الفورية | انشغال أو تحقق أو فتح، والنطاق المتأثر |
| النجاح | النتيجة المرئية والوجهة وتحديث البيانات والتركيز |
| الفشل | موضع الرسالة ومعناها وما يبقى من المدخلات والإجراء التالي |
| التكرار | التعامل مع تكرار الطلب أو الضغط وحدود الإلغاء المعروفة |
| اللغتان | النصوص واتجاهها والمحافظة على السياق عند التبديل |

مثال مستوى الدقة المطلوب: عند فشل جلب القائمة، يظهر خطأ في منطقة النتائج
وتبقى المرشحات. «إعادة المحاولة / Try again» يعيد نفس الاستعلام، ويعرض
انشغالًا في المنطقة المتأثرة؛ عند النجاح تستبدلها النتائج، وعند استمرار
الفشل تبقى وسيلة المحاولة. هذا مثال سلوكي قابل للتكييف، وليس قاعدة ثابتة
لكل خدمة أو وعدًا بوجود تكامل معين.

بيّن عقود البيانات التي يتوقف عليها الشكل: نوع القيمة ومعناها ووحدتها
وغيابها وطولها المتوقع، ومصدر حالات العمل والصلاحيات. إن لم يوجد API
فعلي، سمِّ النموذج مقترحًا أو بيانات تجريبية؛ لا تصف استجابة خادم متخيلة
بأنها متاحة. لا تحسم معمارية الخادم لمجرد استكمال تصميم الشاشة.

## Assets

المسار داخل مهارة الهوية ليس عنوانًا عامًا صالحًا لتطبيق منشور. حلّ الأصل
من الفهرس، وحدد وجهته داخل المشروع. عند تجميع حزمة تنفيذ ضمن النطاق،
انسخ الأصول المختارة اللازمة فعلًا وتحقق من وصول المستلم إليها.

سجل لكل أصل مختار:

| الحقل | الغرض |
| --- | --- |
| معرف الأصل ومرجعه | تحديد الملف الصحيح وإصدار مصدره |
| مسار المصدر النسبي | نسبة إلى جذر مهارة الهوية، مع تحديد اسم المهارة |
| مسار وجهة المشروع | المسار الذي يستخدمه المنفذ، وحالة النسخ: تم أو مطلوب |
| موضع الاستخدام | الشاشة والمكوّن والنسخة والخلفية والمقاس أو القيود |
| خصائص لازمة | الصيغة الفعلية، دقة الصورة أو viewBox، والقص والنص البديل |
| الخطوط | الملف والوجه والوزن الحقيقي وتغطية اللغتين والبديل عند الحاجة |

احفظ الأصل وسياق الترخيص المتاح. لا تفترض أن SVG متجه بالكامل أو أن
ملف Light أو WOFF موجود. حوّل أو أخرج مشتقًا فقط ضمن صلاحيات المهمة
وبالتحقق المناسب، وسجل المشتق دون تغيير مرجع الأصل.

في التسليم إلى محادثة لا تصل إلى الجهاز، أرفق الملفات المختارة المسموح بها
أو بيّن ما يجب أن يصاحب المستند. لا تصف الحزمة بأنها مستقلة إذا كانت
تعتمد على ملف غير مرفق أو رابط لا يستطيع المستلم الوصول إليه.

## Implementation

اجعل نقطة البدء توضح ما يقرأه المطور أولًا، ثم الشاشة أو المسار المقصود،
ثم معايير قبوله. مثال توجيه مختصر يكيف لمسارات المشروع الفعلية:

> اقرأ نقطة البدء والأسس المشتركة، ثم مواصفات المسار المسند إليك.
> طبّق قيم التصميم والمكونات والنصوص العربية والإنجليزية والأصول المحددة
> ضمن تقنية المشروع القائمة. سجل أي تعارض مؤثر، ونفذ فحوص القبول ذات الصلة
> وأرفق دليلًا مرئيًا ونتائج التفاعل التي تحققت فعلًا.

إذا احتاج المشروع توجيهًا خاصًا بـ`AGENTS.md` أو `CLAUDE.md`، اتبع آليته
القائمة وأحِل إلى نفس المواصفات. لا تستبدل تعليمات المشروع الأخرى، وتحقق
من سلوك الأداة الحالي قبل تهيئتها.

عند تعدد الشاشات وتشابهها، قدّم تنفيذ شاشة ممثلة مبكرًا إذا كان سيحسم
الخطوط والكثافة والتجاوب واللغتين. لا تجعل ذلك بوابة موافقة جديدة لم
يطلبها المستخدم. سجّل التغيير المقصود في المصدر التصميمي؛ أما الانحراف
فيوصف بتصحيح واضح وفق [مراجعة التصميم](design-review.md).
