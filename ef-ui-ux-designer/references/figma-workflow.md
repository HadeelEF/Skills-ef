# استخدام Figma في التصميم

الفهرس: [اختيار الاستخدام](#purpose) · [الأدوات](#capabilities) ·
[البناء](#construction) · [التحقق والتسليم](#verification-and-handoff).

## Purpose

استخدم Figma عندما يطلبه المستخدم، أو عند فحص ملف موجود، أو عندما يفيد
التجريب المرئي أو النموذج التفاعلي في حسم قرار مهم ضمن نطاق المهمة.
اختر النطاق المناسب: مكوّن معقد، شاشة ممثلة، مسار خدمة أو مجموعة شاشات.
تظل مواصفات Markdown مسار التسليم المعتاد للمطور.

إذا طلب المستخدم ملف Figma، فهذا مخرج مطلوب يكتمل بملف قابل للوصول
والتحرير وفق الصلاحيات. وإذا كانت المهمة مواصفات فقط، لا تعتبر غياب
Figma نقصًا تلقائيًا. يمكن لشاشة ممثلة باللغتين اختبار الكثافة والهوية
وتوسع النص قبل تكرار النظام في بقية الشاشات.

## Capabilities

تحقق من الأدوات المتاحة واتصال الملف وصلاحيات القراءة أو الكتابة قبل الوعد
بإنشاء تصميم أو تعديل مكتبة. استخدم مهارات Figma المتخصصة المتاحة واقرأ
متطلباتها قبل العملية المقابلة؛ الأسماء التالية مفاتيح اكتشاف في البيئات
التي توفرها، وليست واجهات API ثابتة لكل منصة:

| المهمة | المهارة المناسبة عند توفرها |
| --- | --- |
| إنشاء ملف جديد | `figma-create-new-file` |
| قراءة أو كتابة عناصر التصميم | `figma-use` |
| بناء صفحة أو شاشة | `figma-generate-design` مع `figma-use` |
| مكونات ومتغيرات ومكتبة | `figma-generate-library` مع سير العمل المتاح |
| جلب سياق تصميم للتنفيذ | `figma-design-to-code` |
| مخططات FigJam | `figma-use-figjam` أو `figma-generate-diagram` بحسب العملية |

قد تستخدم بيئة أخرى موصلًا مختلفًا؛ اتبع إمكاناته الفعلية. إذا غابت أداة
ضرورية، أكمل العمل المستقل واذكر ما يتعذر تسليمه. لا تقدّم صورة مسطحة
كملف Figma قابل للتحرير، ولا تنسب القدرة على الكتابة إلى أداة للقراءة فقط.

## Construction

افحص الصفحات والمكونات والأنماط والمتغيرات ذات الصلة في الملف القائم.
أعد استخدام النظام الموجود واحفظ العمل غير المرتبط بالمهمة. افصل
تعديلات المشروع عن إعادة بناء مكتبة مشتركة تؤثر في شاشات أخرى.

- أنشئ نصوصًا وإطارات ومكونات قابلة للتحرير وهرمية مفهومة. استخدم
  Auto Layout وقيود الأحجام حيث يساعد ذلك على تغير المحتوى.
- سمّ الشاشات والمكونات بحسب المهمة، مع معرفات تربطها بمواصفات المشروع.
  جمّع العربية والإنجليزية والأحجام والحالات بطريقة يسهل تتبعها.
- استخدم حالات وخصائص المكونات وإعادة الاستخدام لما يحتاجه التصميم
  فعلًا. لا تنشئ مكتبة ضخمة لأن الأداة تسمح بذلك.
- اكتشف الخطوط والأوجه المتوفرة في الوجهة، وحمّل الوجه الصحيح قبل
  استخدامه. أصل OTF في مرجع الهوية لا يضمن توفره في Figma.
- أدرج أصول EF الأصلية، وافحص الحدود المرئية والنسبة والخلفية.
  راجع الصيغة الفعلية والتدرج والقص بعد الاستيراد.
- ابنِ النسختين العربية والإنجليزية، وافحص التشكيل والاتجاه والطول
  ومحاذاة الأيقونات. لا تعكس إطارًا كاملًا بما فيه الشعار والنصوص.
- حدد سلوك التكيف بالعلاقات والقيود أو متغيرات مناسبة. لقطة الجوال
  وحدها لا تصف ما يحدث بين الأحجام؛ احتفظ بقواعد التجاوب في Markdown.
- اربط النموذج التفاعلي للمسار المطلوب بما تدعمه الأداة. سمِّ الحالات
  المحاكاة بوضوح؛ الانتقال في prototype لا يثبت تشغيل خدمة خلفية.

## Verification and handoff

افحص بنية العناصر من نتائج الأداة، ثم عاين الشاشات بصريًا. أصلح القص
والتداخل والفراغ غير المقصود والخط أو الأصل غير الصحيح. جرّب حالات محتوى
طويل وأخطاء حيث يمكن أن تكسر التكوين، في اللغتين والمقاسات المطلوبة.

سلّم رابط الملف أو الإطار الذي أُنشئ فعلًا، ومعاينة مفيدة عند توفرها،
وما فُحص وما بقي. اربط الشاشات بمعرفاتها في مواصفات المشروع، ودوّن أي
فروق مقصودة بين اللغتين أو الأحجام.

اجعل قرارات الشكل والسلوك النهائية قابلة للتتبع. في تسليم Markdown،
سجّل فيه القرارات المحسومة في Figma كي يستطيع المطور تنفيذها دون استنتاج
تفاصيل ناقصة من الصورة. إذا عيّن المشروع Figma مصدرًا رئيسيًا للشكل،
صرّح بذلك واربطه بمواصفات السلوك والمحتوى؛ عالج أي تعارض قبل تعميمه.
